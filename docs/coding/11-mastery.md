# 11. 고수의 길

**초보자**는 "돌아가는 코드"를 만들고,
**중급자**는 "빠르고 정리된 코드"를 만들고,
**고수**는 "**여러 사람이 오래 고치며 써도 안 무너지는 시스템**"을 만들어요.

---

## 1. 단계별 개발자 모습

| 단계 | 할 수 있는 것 | 주로 하는 고민 |
|---|---|---|
| **입문** | 예제를 따라 쳐서 실행 | "왜 오류가 나지?" |
| **초급** | 혼자 작은 프로그램 완성 | "어떻게 만들지?" |
| **중급** | 남이 읽기 쉬운 코드, 테스트, Git 협업 | "어떻게 정리하지? 더 빠르게?" |
| **고급** | 성능·보안·동시성 문제 해결, 큰 기능 설계 | "왜 느리지? 어디서 터지지?" |
| **고수(시니어·아키텍트)** | 시스템 전체 설계, 기술 선택, 팀 이끌기 | "1년 뒤에도 고치기 쉬울까? 이게 사업에 맞나?" |

---

## 2. 설계 원칙 — 고수들이 공유하는 상식

### SOLID (객체지향 설계 5원칙, 쉬운 버전)
| 원칙 | 쉬운 뜻 |
|---|---|
| **S** 단일 책임 | 클래스·함수 하나는 **한 가지 이유로만** 바뀌어야 한다 |
| **O** 개방-폐쇄 | 기능을 **추가**할 땐 새 코드를 붙이고, 기존 코드는 최대한 안 건드리게 |
| **L** 리스코프 치환 | 자식은 부모 자리에 넣어도 문제없이 동작해야 한다 |
| **I** 인터페이스 분리 | 쓰지도 않는 기능을 억지로 구현하게 만들지 않는다 |
| **D** 의존성 역전 | 구체적인 것(특정 DB)보다 약속(인터페이스)에 기대게 → 갈아 끼우기 쉬움 |

### 그 밖의 유명한 원칙
| 원칙 | 뜻 |
|---|---|
| **KISS** | 단순하게 유지하라 (Keep It Simple) |
| **YAGNI** | 지금 필요 없는 기능은 만들지 마라 (You Aren't Gonna Need It) |
| **DRY** | 같은 지식을 두 군데에 두지 마라 (6장) |
| **관심사의 분리** | 화면·업무 규칙·데이터 저장을 섞지 마라 |

### 디자인 패턴
자주 나오는 설계 문제에 대한 **검증된 해결 모양**이에요. 예: 싱글턴(하나만 존재), 팩토리(객체 생성 담당), 옵저버(구독·알림), 전략(방법 갈아 끼우기), 어댑터(규격 변환기). → 처음부터 외우기보다, 문제를 겪은 뒤에 찾아보면 훨씬 잘 이해돼요.

---

## 3. 코드 리뷰 — 함께 코드 품질을 지키기

**코드 리뷰** = 내 코드를 합치기 전에 동료가 읽어 보고 의견을 주는 것 (GitHub의 Pull Request).

| 리뷰할 때 보는 것 | 예 |
|---|---|
| 맞게 동작하나? | 예외 상황(빈 목록, 0, 아주 큰 값) 처리 |
| 읽기 쉬운가? | 이름, 함수 크기 |
| 테스트가 있나? | 버그 수정엔 그 버그를 잡는 테스트 |
| 보안·성능 문제는? | SQL 인젝션, 반복문 안 DB 호출 |
| 정말 필요한 변경인가? | YAGNI |

좋은 리뷰 매너: **코드를 비판하고 사람을 비판하지 않는다**, 이유를 같이 쓴다, 칭찬도 한다.

---

## 4. 시스템 디자인 — 큰 서비스를 어떻게 설계하나

사용자가 100명일 때와 1,000만 명일 때는 구조가 완전히 달라요.

```
[사용자] → [CDN] → [로드 밸런서] → [웹 서버 여러 대] → [캐시(Redis)]
                                        │                    │
                                        └──→ [메시지 큐] ──→ [작업 서버]
                                        │
                                        └──→ [DB 주 서버] → [DB 복제 서버들]
```

| 부품 | 하는 일 |
|---|---|
| **로드 밸런서** | 손님을 여러 서버에 골고루 나눠 보냄 |
| **수평 확장** | 서버를 **여러 대로** 늘리기 (↔ 수직 확장: 서버 한 대를 더 좋은 걸로) |
| **캐시** | 자주 쓰는 결과를 메모리에 저장 (10장) |
| **DB 복제 / 샤딩** | 읽기용 복사본 두기 / 데이터를 여러 DB에 나눠 담기 |
| **메시지 큐** | 오래 걸리는 일(메일 발송, 영상 변환)을 줄 세워 따로 처리 |
| **CDN** | 사진·파일을 전 세계 가까운 곳에서 (사업 5장) |
| **모니터링·로그** | 어디가 아픈지 보는 눈 (사업 9장) |

### 모놀리스 vs 마이크로서비스
| | 모놀리스 (한 덩어리) | 마이크로서비스 (작은 서비스 여러 개) |
|---|---|---|
| 장점 | 단순, 처음 만들기 빠름 | 팀별로 따로 배포·확장 |
| 단점 | 커지면 고치기 무서움 | 복잡함, 운영 비용 큼 |
| 언제 | **대부분의 작은 회사·초기 서비스** | 큰 조직, 큰 트래픽 |

> 💡 고수일수록 **"작은 팀은 단순한 구조로 시작하라"** 고 말해요. 유행하는 복잡한 구조가 정답이 아닙니다.

---

## 5. 기술 부채와 리팩터링

- **기술 부채** = 급하게 대충 만든 코드가 나중에 이자처럼 시간을 잡아먹는 것.
- **리팩터링** = 동작은 그대로 두고 코드 구조를 개선하는 것. **테스트가 있어야 안심하고** 할 수 있어요 (8장).
- 고수는 "부채 0"을 목표로 하지 않고, **언제 빚을 지고 언제 갚을지**를 판단해요. (출시가 급할 땐 빚을 지고, 자주 고치는 곳부터 갚기)

---

## 6. AI 시대의 고수 — AI 코딩 도구 활용

AI 코딩 도구(Claude Code, GitHub Copilot, Cursor 등)는 이제 많은 현업 개발자의 기본 도구가 됐어요. 고수는 AI를 **"빠른 후배 개발자"** 처럼 써요.

| 고수의 AI 활용 | 설명 |
|---|---|
| **명확한 지시** | 목표, 제약, 파일, 완료 기준을 구체적으로 |
| **작게 나눠 맡기기** | 큰 기능을 단계로 쪼개서 |
| **검증은 내가** | 테스트 실행, 코드 리뷰, 보안 확인 |
| **맥락 제공** | 프로젝트 규칙 문서(예: `CLAUDE.md`), 기존 코드 스타일 |
| **반복 업무 자동화** | 테스트 작성, 문서화, 리팩터링, 오류 원인 추적 |

> ⚠️ AI가 코드를 써 줘도 **설계 판단, 요구사항 이해, 결과 검증, 책임**은 사람에게 남아요. 그래서 기초(4~10장)를 아는 사람이 AI를 훨씬 잘 씁니다. 이 레포가 처음 다뤘던 Stanford CS146S 과목도 바로 이 주제("AI 시대의 소프트웨어 개발")를 다루는 수업이었어요.

---

## 7. 고수가 되는 공부 습관

1. **만들기 → 부수기 → 고치기**를 반복 (작은 프로젝트를 많이 완성)
2. **남의 좋은 코드 읽기** (유명 오픈소스의 작은 부분부터)
3. **오픈소스에 기여** (오타 수정·문서 개선부터 시작해도 OK)
4. **배운 걸 글로 정리** (블로그 — 사업 17장의 정보 사이트가 되기도!)
5. **기초 과목 공부**: 자료구조·알고리즘, 운영체제, 네트워크, 데이터베이스, 컴퓨터 구조
6. **설명할 수 없으면 아직 모르는 것** — 고무 오리에게 설명해 보기 (8장)

### 추천 고전 (개발자들이 자주 권하는 책)
- 『클린 코드』 — 읽기 좋은 코드
- 『리팩터링』 — 코드 개선 방법
- 『실용주의 프로그래머』 — 개발자의 태도와 습관
- 『데이터 중심 애플리케이션 설계』 — 대규모 시스템 (고급)

---

### 이 장 요약
1. 고수는 **오래 고쳐도 안 무너지는 구조**를 만든다: SOLID, KISS, YAGNI, 관심사의 분리.
2. **코드 리뷰·리팩터링·시스템 디자인**이 고급 이후의 핵심. 작은 팀은 **단순한 구조**부터.
3. AI 도구는 빠른 후배처럼 쓰되, **설계·검증·책임은 내가**.
