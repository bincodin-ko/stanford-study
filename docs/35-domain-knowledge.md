# 35. 업계 지식(도메인 지식) — 분야별로 꼭 알아야 할 흐름

> 결제를 실제로 연동하고 정산하는 방법은 [39장](39-payments-and-settlement.md)에 있어요.

개발·기획 현업에서 **"도메인 지식"** 은 사이트 주소가 아니라 **"그 분야의 업무 지식"** 을 말해요.
예: 쇼핑몰 개발자라면 "주문이 어떤 상태를 거쳐 정산까지 가는지", 결제 개발자라면 "승인과 매입이 어떻게 다른지".

> 💡 **왜 중요할까?** 코딩 실력이 같아도, 업계 흐름을 아는 사람이 **실수 없는 기획·설계**를 해요. "부분 환불하면 쿠폰은?", "배송 출발 후 취소는?" 같은 질문에 답할 수 있어야 진짜로 돌아가는 서비스가 됩니다.

> ⚠️ 2026년 10월 조사 기준. 세부 규칙은 회사·계약마다 달라요. ([참고 자료 모음](sources.md))

## 0. 업계 지식을 공부하는 방법

| 방법 | 설명 |
|---|---|
| **용어집 만들기** | 그 분야 단어를 모아 내 말로 정리 (이 자료의 3장처럼) |
| **흐름 그리기** | 돈·물건·정보가 **어디서 어디로, 어떤 순서로** 움직이는지 화살표로 |
| **상태 그리기** | "주문"이 거치는 상태(결제 대기 → 결제 완료 → 배송 중…)를 전부 적기 |
| **예외 찾기** | "중간에 취소하면?", "일부만 환불하면?", "두 번 누르면?" |
| **현장 사람에게 묻기** | CS 담당, 사장님, 정산 담당의 실제 고민이 가장 좋은 교재 |
| **경쟁 서비스 직접 써 보기** | 주문·취소·환불까지 해 보면 업계 관례가 보임 |

### 개발 쪽에서 쓰는 말: 도메인 주도 설계(DDD)
- **유비쿼터스 언어(공통 언어)**: 기획자·현업·개발자가 **같은 단어를 같은 뜻으로** 쓰고, 코드 이름도 그 단어로 짓기. (예: 현업이 "출고"라고 하면 코드도 `ship()`이 아니라 출고의 뜻이 담긴 이름으로)
- **바운디드 컨텍스트(경계)**: 같은 단어도 부서마다 뜻이 달라요. "주문"은 판매팀에선 "손님이 산 것", 물류팀에선 "보내야 할 상자". 그래서 **영역을 나누고 영역마다 단어 뜻을 하나로** 정해요.
- 복잡한 업무일수록 효과가 크고, 작은 프로젝트에는 과할 수 있어요. ([코딩 11장](coding/11-mastery.md) 설계 원칙과 연결)

## 1. 이커머스(쇼핑몰) 도메인

### 주문 상태 흐름
```
장바구니 → 주문서 작성 → 결제 대기 → 결제 완료
   → 상품 준비 중 → 출고(배송 시작) → 배송 중 → 배송 완료 → 구매 확정
                                 ↘ 취소 / 교환 / 반품 → 환불
```

| 용어 | 뜻 | 실무 포인트 |
|---|---|---|
| **SKU** | 재고 관리 최소 단위 (같은 티셔츠라도 색·사이즈마다 다른 SKU) | 재고는 SKU 단위로 셈 |
| **옵션** | 색상·사이즈 등 | 옵션 조합이 곧 SKU |
| **재고 차감 시점** | 주문 시 / 결제 완료 시 | 결제 완료 시 차감이 흔함. 동시 결제 시 **경쟁 상태** 주의 ([코딩 10장](coding/10-advanced.md)) |
| **품절·일시품절** | | 위탁판매는 도매처 재고와 연동 (23장) |
| **객단가·장바구니 이탈** | | 11장 지표 |
| **쿠폰·적립금** | 할인 수단 | **부분 환불 시 쿠폰을 어떻게 나눌지** 미리 규칙 정하기 |
| **구매 확정** | 손님이 "받았어요" 확인 (또는 일정 기간 후 자동) | 오픈마켓은 구매 확정 후 정산되는 경우가 많음 |
| **클레임** | 취소·교환·반품을 묶어 부르는 말 | 청약철회 규칙 (10장) |
| **CS 사유 코드** | 단순 변심 / 상품 불량 / 오배송 | **누가 배송비를 내는지** 갈림 |

### 꼭 정해 둘 예외 규칙
- 결제 후 **출고 전 취소** → 즉시 환불
- **출고 후 취소** → 반품으로 전환, 회수 후 환불
- **일부 상품만 반품** → 무료배송 기준 미달 시 배송비 차감 여부
- **교환 재고가 없을 때** → 환불로 전환

## 2. 결제(페이먼트) 도메인

### 카드 결제 흐름: 승인 → 매입 → 정산
```
손님 결제 버튼
  → [승인] PG사가 카드사에 "이 카드로 이 금액 결제 가능?" → 한도 확보 (돈이 실제로 움직인 건 아님)
  → [매입] 판매가 확정되면 카드사에 "이 승인 건 청구해 주세요" (보통 매일 묶어서)
  → [정산] 카드사 → PG사 → 판매자 통장 (수수료 빼고, D+N일 후)
```

| 용어 | 뜻 |
|---|---|
| **PG(결제 대행사)** | 쇼핑몰과 카드사 사이에서 결제를 중개 (10장) |
| **승인 / 승인 취소** | 결제 가능 여부 확인 / 매입 전 취소 (대개 바로 한도 복구) |
| **매입 / 매입 취소** | 실제 청구 확정 / 확정 후 취소 (환불이 며칠 걸리는 이유) |
| **정산 주기 (D+N)** | 결제일로부터 N일 뒤 입금. 일·주·월 단위로 계약. N일은 취소·분쟁 대비 기간이라는 설명이 많음 |
| **부분 취소** | 일부 금액만 취소 (일부 상품 반품) — 결제 수단마다 지원 여부가 다름 |
| **간편결제** | 카카오페이·네이버페이·토스페이 등 |
| **가상계좌 / 계좌이체** | 입금 확인 후 결제 완료 처리 |
| **에스크로** | 돈을 잠시 맡아 두는 구매안전서비스 (10장) |
| **정기결제(빌링)** | 처음에 카드를 등록해 **빌링키**를 받고, 이후 매달 자동 결제 (구독 서비스 필수). 빌링키 발급 때 **본인 확인**이 중요하다는 안내가 있어요 |
| **차지백** | 손님이 카드사에 "내가 한 결제가 아니다/물건 못 받았다"고 이의 제기해 대금이 회수되는 것. 해외 결제에서 특히 주의 |
| **PCI DSS** | 카드 정보 보안 국제 기준 → 그래서 카드번호는 직접 저장하지 않고 PG에 맡김 (10장) |
| **멱등성(idempotency)** | 결제 버튼을 두 번 눌러도 **한 번만 결제**되게 하는 설계. 결제 개발의 핵심 |

### 실무에서 자주 터지는 곳
- 결제는 됐는데 **우리 서버가 결과를 못 받음**(네트워크 끊김) → 주문은 "결제 대기"인데 돈은 빠짐 → **PG 결제 내역과 우리 주문을 매일 대조(대사)** 하는 작업 필요
- 구독 결제 실패(카드 만료·한도 초과) → 재시도 일정, 손님 안내, 서비스 중지 시점 정하기

## 4. 광고(애드테크) 도메인

18·31장에서 "광고를 붙여 돈 벌기"를 봤다면, 여기선 **광고가 어떻게 거래되는지**예요.

```
광고주 → [DSP] ─┐
                ├→ [애드 익스체인지: 실시간 경매] ←─ [SSP] ← 사이트 운영자(퍼블리셔)
광고주 → [DSP] ─┘           ↑
                       [DMP: 데이터]
손님이 페이지를 여는 순간 → 경매 → 이긴 광고가 표시 (보통 0.1초 안에)
```

| 용어 | 뜻 |
|---|---|
| **퍼블리셔** | 광고 자리를 가진 사이트·앱 운영자 (나!) |
| **SSP** | 퍼블리셔 쪽 플랫폼: 광고 자리를 **팔아 줌** |
| **DSP** | 광고주 쪽 플랫폼: 광고 자리를 **사 줌** |
| **애드 익스체인지** | 둘이 만나는 **경매장** (증권거래소 비유) |
| **RTB (실시간 입찰)** | 광고 노출 한 번마다 실시간 경매 |
| **DMP** | 광고용 데이터 모음·분류 |
| **인벤토리** | 팔 수 있는 광고 자리·노출 수 |
| **필레이트** | 광고 요청 중 실제로 광고가 채워진 비율 |
| **어트리뷰션** | 구매가 **어느 광고 덕분인지** 나누어 계산하는 것 |
| **퍼스트파티 / 서드파티 데이터** | 내가 직접 모은 데이터 / 남(광고 회사 등)이 여러 사이트에서 모은 데이터 |
| **서드파티 쿠키** | 다른 사이트를 오가며 사용자를 추적하던 쿠키. 개인정보 문제로 브라우저들이 제한해 왔고, 크롬의 정책은 여러 번 바뀌었어요 → 그래서 **퍼스트파티 데이터(회원·구독자)** 가 더 중요해짐 |

| **원장(ledger)** | 돈의 모든 움직임을 기록하는 장부. **잔액은 원장에서 계산**하고 함부로 덮어쓰지 않음 |
| **복식부기** | 모든 거래를 "어디서 빠지고 어디로 들어갔는지" 두 줄로 기록 |
| **대사(reconciliation)** | 우리 기록과 은행·PG 기록을 맞춰 보기 (2절) |
| **선불 충전금** | 포인트·머니를 현금처럼 쓰게 하면 규제 대상이 될 수 있음 (29장) |
| **이상 거래 탐지(FDS)** | 평소와 다른 결제·로그인 패턴 차단 |

## 11. 분야별 "한 장 요약" 만들기 연습

새 분야를 공부할 때 아래 표를 채워 보세요. 다 채우면 그 분야의 기본 도메인 지식이 생긴 거예요.

```
분야 이름:
1. 누가 누구에게 무엇을 파는가?          (1·22장)
2. 돈은 어떤 순서로 움직이나?            (결제·정산 흐름)
3. 물건/서비스는 어떤 상태를 거치나?      (상태 흐름도)
4. 가장 흔한 예외 5가지는?               (취소, 부분 환불, 노쇼…)
5. 이 분야만의 숫자(지표) 3개는?
6. 이 분야만의 법·규제는?                (29장)
7. 현업 사람들이 쓰는 단어 20개 (용어집)
```

---

### 이 장 요약
1. 도메인 지식 = **그 분야의 업무 흐름과 단어**. 흐름·상태·예외를 그려 보며 공부한다.
2. 핵심 흐름: **주문 상태(커머스), 승인→매입→정산(결제), 입고→출고→배송(물류), DSP↔SSP 경매(광고), 라이브 옵스(게임), 더닝·프로레이션(구독), 원장·대사(금융)**.
3. 개발에선 **공통 언어와 영역 나누기(DDD)** 로 업무 지식을 코드에 담는다.
