# 07. 업데이트와 배포 — 멈추지 않고 고치는 법

**배포(Deploy)** = 고친 내용을 실제 사이트에 반영하는 것.
목표는 딱 두 가지예요.
1. 손님이 **눈치채지 못하게** 바꾸기
2. 문제가 생기면 **몇 분 안에 되돌리기(롤백)**

---

## 1. 업데이트의 종류

| 종류 | 예 | 위험도 | 방법 |
|---|---|---|---|
| **콘텐츠 수정** | 상품 가격, 배너, 공지 | 낮음 | 관리자 페이지에서 바로. 단, 가격은 두 번 확인 |
| **디자인 수정** | 버튼 색, 메인 화면 배치 | 중간 | 테스트 스킨/스테이징에서 확인 후 적용 |
| **기능 추가·수정** | 쿠폰 기능, 결제 방식 추가 | 높음 | 브랜치 → 스테이징 → 배포 (6장 흐름) |
| **DB 구조 변경** | 회원 정보에 "생일" 칸 추가 | **매우 높음** | 배포 직전 **DB 백업 필수**, 되돌리는 방법 먼저 준비 |
| **보안 패치** | 플러그인·서버 프로그램 업데이트 | 높음(안 하면 더 위험) | 스테이징에서 먼저 → 빠르게 운영 반영 |
| **핫픽스** | "결제가 안 돼요!" 긴급 수정 | 긴급 | 최소한만 고쳐서 바로 배포, 나중에 제대로 정리 |

---

## 2. 표준 배포 절차 (작은 팀용)

```
1. 변경 내용 정리        무엇을 왜 바꾸는지 한 줄로 적기
2. 백업               DB 백업 + 지금 운영 중인 버전 번호 기록
3. 스테이징 확인         핵심 흐름(가입→구매→결제) 직접 해 보기
4. 배포 시간 고르기       손님이 가장 적은 시간 (보통 평일 오전 / 새벽)
                       ❌ 금요일 저녁·연휴 전날·대형 이벤트 직전은 피하기
5. 배포
6. 운영 사이트 확인       배포 직후 10~30분: 주문 들어오는지, 오류 늘었는지
7. 기록               변경 이력(릴리스 노트)에 남기기
   문제 발생 시 →       고치려 하지 말고 "먼저 롤백", 원인은 그다음에
```

> **"먼저 되돌리고, 나중에 고친다."** 운영 중 장애에서 가장 중요한 원칙.
> 손님이 오류를 보는 시간을 줄이는 게 원인 찾기보다 우선이에요.

---

## 3. 손님 몰래 바꾸는 배포 기법 (중급)

| 기법 | 비유 | 어떻게 | 되돌리기 |
|---|---|---|---|
| **블루-그린 배포** | 무대 두 개 | 운영(블루) 옆에 새 버전(그린)을 똑같이 띄워 두고, 손님 입구만 그린으로 바꿈 | 입구를 다시 블루로 → 몇 초~몇 분 |
| **카나리 배포** | 탄광의 카나리아 | 새 버전을 손님 1% → 10% → 50% → 100% 순서로 조금씩 보여 줌 | 이상하면 비율을 0%로 |
| **기능 플래그** | 전등 스위치 | 새 기능 코드를 미리 배포해 두고 스위치를 꺼 둠 → 준비되면 켬 | 스위치만 끄면 끝 (재배포 불필요) |
| **점검 모드** | "잠시 공사 중" 팻말 | 큰 변경 때 공지 후 잠깐 사이트를 막음 | — |

- 블루-그린은 서버가 두 배 필요해서 비용이 더 듭니다.
- 카나리는 "이상한지"를 알아채는 **모니터링**(9장)이 꼭 있어야 의미가 있어요.
- DB 구조를 바꿀 때는 **옛 버전과 새 버전이 둘 다 돌아가도록** 단계적으로 바꿉니다. (예: 칸을 "추가"만 먼저 하고, 옛 칸 "삭제"는 한참 뒤에)

---

## 4. 자동화 — CI/CD

손으로 하면 실수가 생기므로, 규모가 커지면 자동화합니다.

- **CI(지속적 통합)**: 코드를 올리면 자동으로 테스트가 돌아가서 "깨졌는지" 알려 줌.
- **CD(지속적 배포)**: 테스트를 통과하면 자동으로 스테이징/운영에 배포.
- 도구 예: GitHub Actions, Vercel 자동 배포 등.

> 혼자 빌더로 운영한다면 CI/CD는 필요 없어요. **2번 절차표**만 지켜도 충분합니다.

## 5. 버전 번호 붙이기

`v1.4.2` 같은 번호는 보통 이런 규칙이에요(**시맨틱 버저닝**).

| 자리 | 언제 올리나 | 예 |
|---|---|---|
| **1** (Major) | 큰 개편, 예전과 호환 안 됨 | 사이트 전면 리뉴얼 |
| **4** (Minor) | 새 기능 추가 | 쿠폰 기능 추가 |
| **2** (Patch) | 버그 수정 | 오타, 버튼 오류 수정 |

---

## 6. 손님에게 알리기

- 작은 변경: 알릴 필요 없음.
- 손님이 쓰는 방식이 바뀜: **공지사항 + 화면 안내**.
- 점검으로 사이트를 멈춤: **최소 며칠 전 공지**, 시작·종료 시간 명시.
- 가격·약관 변경: 법적으로 **미리 알릴 의무**가 있는 경우가 있음 (10장).

---

### 이 장 요약
1. 배포 전 **백업**, 배포 후 **확인**, 문제가 생기면 **먼저 롤백**.
2. 금요일 저녁·이벤트 직전 배포는 피한다.
3. 블루-그린·카나리·기능 플래그 = 손님 몰래 바꾸고 바로 되돌리는 기술.
