# 39. 결제 연동과 정산 처리

35장에서 결제의 흐름(승인 → 매입 → 정산)을 개념으로 봤어요.
이 장은 **실제로 내 사이트에 결제를 붙이고(연동), 들어온 돈을 맞춰 보고(대사), 판매자에게 나눠 주는(정산)** 방법이에요.

> ⚠️ 2026년 10월 조사 기준. API 이름·규칙은 PG사마다 다르고 자주 바뀌어요. 실제 개발은 **내가 계약한 PG사의 공식 개발자 문서**를 기준으로 하세요. 아래 코드는 흐름을 이해하기 위한 **개념용 의사코드**예요. ([참고 자료 모음](sources.md))

---

## 1. 결제 붙이는 3가지 방법

| 방법 | 설명 | 추천 대상 |
|---|---|---|
| **① 빌더 내장 결제** | 카페24·아임웹 등에서 "결제 설정" 메뉴로 PG 신청 | 쇼핑몰 빌더 사용자 — **코딩 없음** |
| **② PG사 직접 연동** | 토스페이먼츠, KG이니시스, NHN KCP, 나이스페이 등과 계약하고 그 회사의 결제창·API를 붙임 | 직접 개발한 서비스 |
| **③ 결제 통합 플랫폼** | 포트원(PortOne) 같은 곳을 통해 **여러 PG를 한 가지 코드로** 연동 | PG를 바꾸거나 여러 개 쓰고 싶을 때 |

- 포트원은 스스로를 **PG가 아니라 "PG 연동을 도와주는 플랫폼"** 이라고 설명해요. 실제 계약은 **가맹점(나)과 PG사**가 맺어요.
- 간편결제(카카오페이·네이버페이·토스페이 등)는 PG를 통해 함께 붙이거나 따로 계약하는 경우가 있어요.

## 2. PG 계약 절차 (직접 연동 기준)

```
1. 사업자등록 + 통신판매업 신고 (10장)
2. PG사(또는 통합 플랫폼)에 전자결제 신청
   - 필요 서류 예: 사업자등록증, 서비스 URL, 대표자·담당자 정보, 통장 사본
3. PG사 심사 — 업종·사이트 확인 (상품·가격·환불 정책·사업자 정보 표시가 사이트에 있어야 함)
4. 보증보험 가입 요구가 있을 수 있음 (PG사별)
5. 계약 완료 → 실서비스용 키(라이브 키) 발급
6. 개발은 그 전에 테스트 키로 미리 진행
```

### 실전 팁
- **업종 심사를 먼저 확인**: 수수료보다 "우리 업종을 받아 주는지"가 먼저예요. 업종에 따라 반려될 수 있어요(29장 규제 업종).
- **사이트가 완성된 상태로 신청**: 심사 때 상품 페이지, 가격, 교환·환불 정책, 사업자 정보 푸터를 봐요 (38장).
- **PG 수수료**는 결제 수단·업종·매출 규모에 따라 다르고, 통합 플랫폼 자료에는 보통 1~3%대라고 소개돼요. 견적을 여러 곳 비교하세요.
- PG사 연락이 **스팸함**으로 가는 일이 흔하다는 안내가 있어요.

## 3. 결제 연동의 기본 흐름 (요청 → 인증 → 승인)

```
[손님 브라우저]                [내 서버]                     [PG사]
 1. "결제하기" 클릭
                    2. 주문 생성 (주문번호, 금액을 DB에 "결제 대기"로 저장)
 3. PG 결제창 열기 (주문번호·금액 전달)  ───────────────────▶  4. 카드 정보 입력·본인 인증
                                                             (카드 정보는 PG가 받음. 내 서버엔 안 옴)
 5. 성공 주소(successUrl)로 이동  ◀──── paymentKey, orderId, amount ────
                    6. ★ 금액 검증: 받은 amount == DB에 저장한 금액?
                    7. ★ 승인 API 호출 (서버 ↔ PG, 비밀 키 사용) ──────▶  8. 실제 승인
                    9. 승인 결과 저장 (paymentKey 보관), 주문 "결제 완료"
 10. 완료 페이지 표시
```

### 왜 ★ 두 단계가 핵심인가
| 단계 | 이유 |
|---|---|
| **금액 검증** | 브라우저에서 넘어온 값은 **조작 가능** (37장). 손님이 10만 원짜리 주문의 금액을 100원으로 바꿔 결제창을 열 수도 있어요. **서버에 저장해 둔 금액과 같을 때만** 승인 |
| **서버에서 승인** | 승인 요청엔 **비밀 키(시크릿 키)** 가 필요해요. 비밀 키는 **서버에만** 두고 브라우저 코드에 절대 넣지 않아요 |

- 토스페이먼츠 문서·블로그 기준으로는 성공 주소로 받은 `paymentKey`, `orderId`, `amount`가 **처음 요청한 값과 같은지 확인한 뒤** 승인 API를 호출하고, `paymentKey`는 이후 **취소·조회에 필요하니 DB에 저장**하라고 안내해요.
- 결제 인증 후 **일정 시간(예: 10분이라는 안내가 있음) 안에 승인하지 않으면 만료**될 수 있어요. 공식 문서로 확인하세요.

### 개념용 의사코드 (서버)
```python
# ⚠️ 흐름 이해용 의사코드 — 실제 API 주소·형식은 PG사 공식 문서를 따르세요
def on_payment_success(payment_key, order_id, amount):
    order = db.get_order(order_id)
    if order is None or order.status != "결제대기":
        return error("이상한 주문")
    if amount != order.amount:                 # ★ 금액 검증
        return error("금액 불일치 — 승인하지 않음")

    result = pg.confirm(                       # ★ 서버에서 비밀 키로 승인
        payment_key, order_id, amount,
        secret_key=env("PG_SECRET_KEY"),       # 비밀 키는 환경 변수
        idempotency_key=order_id,              # 같은 요청이 두 번 가도 한 번만 처리
    )
    if result.ok:
        db.update_order(order_id, status="결제완료", payment_key=payment_key)
        send_receipt(order)
    else:
        db.update_order(order_id, status="결제실패", reason=result.message)
```

## 4. 웹훅 — PG가 나에게 알려 주는 알림

**웹훅** = PG사가 "이 결제 상태가 바뀌었어요"라고 **내 서버 주소로 자동으로 보내 주는 알림**이에요.

| 이럴 때 필요 | 예 |
|---|---|
| **가상계좌·무통장** | 손님이 나중에 입금 → 입금 완료를 웹훅으로 받아 주문을 "결제 완료"로 |
| **승인 응답을 못 받았을 때** | 네트워크가 끊겨 5단계 이후 처리가 안 됐어도, 웹훅으로 최종 상태를 받음 |
| **취소·환불·정기결제 실패** | 상태 변화를 놓치지 않게 |

### 웹훅을 안전하게 받는 4가지 규칙
1. **진짜 PG가 보낸 건지 확인**: 서명 검증이 있으면 반드시 검증(받은 원본 그대로로 검증), 없다면 **PG 조회 API로 상태를 다시 확인**한 뒤 반영
2. **같은 알림이 여러 번 올 수 있다**: 결제 업계 웹훅은 보통 "최소 한 번" 전달이라, **같은 이벤트 ID는 한 번만 처리**(DB 고유 키)
3. **빨리 대답**: 받자마자 저장하고 "200 OK"를 돌려준 뒤, 무거운 작업(메일 발송 등)은 따로 처리. 느리면 PG가 재전송
4. **순서가 뒤바뀔 수 있다**: "취소" 알림이 "완료"보다 먼저 올 수도 있으니 **현재 상태를 기준으로** 판단

## 5. 꼭 처리해야 할 예외 상황

| 상황 | 처리 |
|---|---|
| **결제 버튼 두 번 클릭** | 버튼 비활성화 + 서버에서 같은 주문 중복 승인 막기(멱등성, 35장) |
| **돈은 빠졌는데 주문은 "결제 대기"** | 웹훅·조회 API로 상태 동기화, 매일 **대사**(6절)로 찾아내기 |
| **승인 후 우리 DB 저장 실패** | 재시도 → 그래도 실패하면 **결제 취소 API**로 되돌리고 손님에게 안내 |
| **재고 동시 소진** | 결제 전 재고 확인 + 승인 직전 재확인, 부족하면 승인하지 않음 ([코딩 10장](coding/10-advanced.md) 경쟁 상태) |
| **부분 취소** | 일부 상품 반품 시 취소 금액 계산(쿠폰·배송비 배분 규칙, 35장), PG 부분 취소 API |
| **정기결제 실패** | 재시도 일정(예: 1·3·7일 후), 손님 알림, 유예 기간 뒤 서비스 중지 (더닝, 35장) |
| **해외 카드 차지백** | 배송·이용 증빙 보관, 이의 제기 대응 |

## 6. 대사 — 매일 돈 맞춰 보기

**대사(reconciliation)** = 내 DB의 결제 기록과 **PG사의 거래 내역**을 한 건씩 맞춰 보는 일이에요.

```
매일 아침 (자동화 추천)
1. PG 관리자 페이지·API에서 어제 거래 내역 받기 (승인·취소·부분취소)
2. 우리 DB의 어제 결제·취소 목록과 주문번호로 짝 맞추기
3. 차이 찾기:
   - PG엔 있는데 우리 DB엔 없음 → 결제됐는데 주문 누락! (가장 위험)
   - 우리 DB엔 있는데 PG엔 없음 → 실제로 돈이 안 들어온 주문
   - 금액이 다름 → 부분 취소 반영 누락 등
4. 차이 건은 담당자에게 알림 → 원인 확인 후 수정
```
그리고 **정산일**에는 "PG가 보내 준 정산 금액 = 매출 − 취소 − 수수료(− 부가세 등)"가 맞는지 확인해요 (14장 매월 점검의 "PG 정산 금액 대조").

## 7. 정산 — 돈이 내 통장에 들어오기까지

### 내가 판매자일 때 (쇼핑몰)
| 항목 | 내용 |
|---|---|
| **정산 주기** | PG와 계약으로 정함 (일·주·월 정산, D+N일). N일은 취소·분쟁 대비 기간이라는 설명이 많음 |
| **수수료** | 결제 수단별로 다름. 정산 금액에서 빠짐 |
| **보류** | 분쟁·이상 거래가 있으면 정산이 보류될 수 있음 |
| **현금 흐름** | 오늘 판 돈이 며칠 뒤 들어옴 → 원재료·광고비 결제일과 맞춰 계획 |

### 내가 플랫폼일 때 (판매자에게 나눠 줌, 27장)
중개 플랫폼은 **손님에게 받은 돈에서 수수료를 떼고 판매자에게 정산**해야 해요.

```
손님 결제 10만 원
  → PG 수수료 (예: 약 3%)
  → 플랫폼 수수료 (예: 10%)
  → 판매자 정산 금액 = 10만 원 − 플랫폼 수수료 (PG 수수료는 계약에 따라 누가 낼지 정함)
  → 정산 기준일: 구매 확정일 (또는 서비스 이용일)
```

| 해야 할 것 | 설명 |
|---|---|
| **정산 원장** | 판매자별로 "판매 · 취소 · 수수료 · 지급 · 미지급 잔액"을 한 줄씩 기록. **덮어쓰지 않고 추가만** (35장 금융 원장) |
| **정산서** | 판매자에게 기간별 내역 공개 |
| **지급 방법** | 플랫폼 계좌에서 직접 송금하거나, PG의 **지급대행(정산대행)** 서비스 이용. 남의 돈을 맡아 두는 구조는 전자금융 규제 이슈가 있을 수 있어 **PG의 지급대행**을 많이 써요 (29장) |
| **세금** | 플랫폼 수수료에 대한 세금계산서 발행 등 → 세무사 확인 |

### 법: 정산 기한과 판매대금 보호 (티메프 사태 이후)
- 2024년 대형 이커머스(티몬·위메프)의 판매대금 미정산 사태 이후, 공정위가 **대규모유통업법 개정 방향**을 확정했어요(2024년 10월 발표 기준):
  - 대상: 국내 중개거래 매출 100억 원 이상 또는 거래액 1,000억 원 이상의 B2C 온라인 중개거래 사업자
  - **구매 확정일로부터 20일 이내 정산** (숙박·여행·공연 등은 이용일 기준 10일)
  - 플랫폼이 직접 대금을 관리하면 **판매대금 50% 이상을 별도 예치**하거나 지급보증보험 가입
  - 공포 후 1년 유예, 정산 기한·별도 관리 비율은 단계적으로 강화하는 계획
- 국회 통과·실제 시행일은 이번 조사에서 확인하지 못했어요. **작은 플랫폼이라도 "정산은 약속한 날 반드시"** 가 신뢰의 핵심이에요.

| **세금계산서** | 사업자 손님(B2B)이 요청하면 발행 |
| **간이·일반과세** | 10장 |

## 9. 결제 연동 체크리스트 (출시 전)

- [ ] 테스트 키로 **카드·간편결제·가상계좌·취소·부분취소** 전부 테스트
- [ ] 비밀 키는 서버 환경 변수에만, 브라우저 코드·Git에 없음
- [ ] 서버에서 **금액 검증 후 승인**
- [ ] 중복 승인 방지(멱등성), 결제 버튼 중복 클릭 방지
- [ ] 웹훅: 출처 검증, 중복 처리 방지, 빠른 200 응답
- [ ] 승인 후 DB 저장 실패 시 자동 취소 또는 알림
- [ ] `paymentKey` 등 결제 식별자 저장
- [ ] 매일 대사 자동화, 정산일 금액 대조

### 이 장 요약
1. 결제는 **빌더 내장 / PG 직접 / 통합 플랫폼** 중 선택. 계약은 업종 심사가 먼저, 개발은 테스트 키로 먼저.
2. 핵심 흐름: **주문 저장 → 결제창 → 서버에서 금액 검증 → 비밀 키로 승인 → 저장**. 웹훅은 **출처 검증·중복 방지·빠른 응답**.
3. 매일 **대사**로 PG와 DB를 맞추고, 플랫폼이라면 **정산 원장 + 지급대행 + 약속한 정산일 지키기**.
