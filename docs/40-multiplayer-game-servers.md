# 40. 멀티플레이 게임 서버 — 롤·배그는 어떻게 동시에 같이 할까

20장에서는 1:1 턴제 게임(오목) 서버를 봤어요. 오목은 한 수씩 번갈아 두니까 조금 늦어도 괜찮지만,
**리그 오브 레전드(롤)·배틀그라운드(배그)·발로란트** 같은 게임은 수십~100명이 **동시에, 1초에 수십 번씩** 움직여요.
이 장은 그런 **실시간 멀티플레이 게임의 서버와 백엔드 구조**를 쉽게 풀어 봐요.

> ⚠️ 각 게임 회사의 내부 구조는 대부분 공개돼 있지 않아요. 아래는 **공개된 기술 블로그·개발자 문서·업계 자료**로 정리한 일반적인 구조예요. ([참고 자료 모음](sources.md))

## 1. 큰 그림 — 게임 하나 뒤에 있는 서버들

```
[게임 클라이언트(내 PC·폰)]
   │ 로그인·친구·상점·매칭 요청 (HTTPS, 몇 초 늦어도 OK)
   ▼
┌──────────── 백엔드 서비스들 (웹 서비스와 비슷) ────────────┐
│ 로그인/계정 · 친구/채팅 · 상점/결제 · 인벤토리 · 랭킹/전적 │
│ 매치메이킹(실력 비슷한 사람 모으기) · 공지/점검 · 부정행위 탐지 │
└───────────────────────┬───────────────────────────────┘
                        │ "10명 모였다! 게임 서버 하나 줘"
                        ▼
               [게임 서버 관리(오케스트레이션)]
                        │ 빈 게임 서버 배정 (주소·접속 토큰 전달)
                        ▼
[게임 클라이언트들] ⇄ (UDP, 초당 수십 번) ⇄ [전용 게임 서버 1판]
                                              │ 경기 끝 → 결과 전송
                                              ▼
                                    전적·랭크 점수·보상 저장 (백엔드)
```

| 구분 | 하는 일 | 특징 |
|---|---|---|
| **백엔드 서비스** | 계정, 친구, 채팅, 상점, 인벤토리, 전적, 매칭 | 일반 웹 서버와 비슷 ([코딩 9장](coding/09-web-development.md)). 조금 늦어도 괜찮음 |
| **전용 게임 서버(Dedicated Server)** | 한 판(매치) 안의 실제 게임 진행 | **초당 수십 번 계산**, 지연에 매우 민감, 한 판 끝나면 사라짐 |
| **오케스트레이션** | 게임 서버를 필요한 만큼 켜고 끄고 배정 | 사람이 몰리면 자동으로 늘림 |

예: 롤(Riot)은 채팅을 지역별로 따로 운영하는 별도 클러스터(얼랭 언어 기반)로 만들었다고 기술 블로그에 공개했어요. 로그인·채팅·매칭·게임 서버가 **각각 다른 서비스**로 나뉘어 있다는 뜻이에요.

## 2. 네트워크 구조 3가지

| 구조 | 설명 | 장점 | 단점 | 쓰이는 곳 |
|---|---|---|---|---|
| **P2P (서로 직접 연결)** | 플레이어 컴퓨터끼리 직접 통신 | 서버 비용 거의 0 | 치팅 막기 어려움, 한 명이 느리면 모두 느림 | 1:1 격투 게임, 일부 협동 게임 |
| **호스트 방식(리슨 서버)** | 플레이어 한 명이 서버 역할 | 저렴 | 호스트가 유리, 호스트가 나가면 판이 깨짐 | 친구끼리 하는 소규모 게임 |
| **전용 서버 + 서버 권위** | 회사가 운영하는 서버가 모든 판정 | **공정, 치팅 방지** | 서버 비용 큼 | **롤·배그·발로란트 같은 경쟁 게임** |

### 서버 권위(Authoritative Server)가 원칙
- "누가 맞았나, 어디에 있나, 체력이 얼마인가"는 **서버만 결정**해요. 클라이언트는 **"앞으로 가기 버튼 눌렀어요"** 같은 **입력만** 보내요.
- 클라이언트가 "나 순간이동했어", "내 체력 100이야"라고 보내는 걸 믿으면 해킹 천국이 돼요 (20장 오목의 "판정은 서버가"와 같은 원리).
- 발로란트는 처음부터 공정성과 치팅 방지를 위해 **서버 권위 구조**로 만들었다고 소개돼요.

## 3. 틱 레이트 — 서버가 1초에 몇 번 세상을 계산하나

**틱(tick)** = 서버가 입력을 모아 세상을 한 번 계산하는 단위. **틱 레이트** = 1초에 몇 틱.

| 게임 (공개 자료 기준) | 틱 레이트 |
|---|---|
| 발로란트 | **128틱** (Riot 공식 기술 블로그) |
| 소스 엔진 게임(예전 CS 등) | 66틱 (Valve 개발자 위키) |
| 포트나이트 배틀로얄 초기 목표 | 100명 동시 + **20Hz 유지** (에픽 기술 블로그) |

### 틱 레이트는 공짜가 아니다
- Riot은 128틱을 위해 **한 프레임을 7.8125ms 안에 계산**해야 했고, 처음엔 게임 하나가 CPU 코어 하나를 통째로 써서 너무 비쌌다고 밝혔어요. 그래서 엄청난 최적화를 했어요.
- 업계 분석에 따르면 **틱 레이트를 두 배로 올리면 CPU와 대역폭도 대략 두 배**가 들어요.
- 배그는 2018년 "Fix PUBG" 캠페인 때, **많은 플레이어가 한곳에 몰리는 초반(낙하·첫 자기장)** 에 서버 처리가 밀려 틱 레이트가 크게 떨어지는 문제가 있었다고 보도됐어요. → **100명 게임은 "누구에게 무엇을 보낼지" 줄이는 최적화**가 핵심이에요.

## 4. 지연(핑)을 숨기는 4가지 기술

인터넷은 느려요. 서울↔서버 왕복이 30ms만 돼도, 버튼을 누를 때마다 30ms씩 늦게 움직이면 답답해요. 그래서 게임은 **지연을 "숨기는"** 기술을 써요. (개발자 가브리엘 감베타의 "Fast-Paced Multiplayer" 글 시리즈가 이 분야 입문 교재로 유명해요.)

### ① 클라이언트 예측 (Client-side Prediction)
- 내가 앞으로 가기를 누르면, **서버 답을 기다리지 않고 내 화면에서 바로** 움직여요(예측).
- 동시에 서버에도 입력을 보내요.

### ② 서버 보정 (Server Reconciliation)
- 서버 답이 오면 "서버가 계산한 진짜 위치"와 비교해요.
- 다르면 **서버 위치로 맞춘 뒤, 아직 서버가 처리 안 한 내 입력들을 다시 적용**해요. (그래서 가끔 캐릭터가 살짝 "끌려가는" 느낌 = 보정)

### ③ 엔티티 보간 (Entity Interpolation)
- **다른 플레이어**는 예측하기 어려워서, 서버에서 받은 **지난 위치 두 개 사이를 부드럽게 이어서** 보여 줘요.
- 대신 다른 사람은 **약간 과거 모습**으로 보여요. 소스 엔진은 기본 100ms 보간을 쓴다고 Valve 위키에 나와요.

### ④ 지연 보상 (Lag Compensation)
- 내가 총을 쏜 순간 내 화면 속 적은 "약간 과거 위치"예요.
- 서버는 **내 핑 + 보간 시간만큼 시간을 되감아서** "쏜 순간 실제로 맞았나"를 판정해요. Valve 위키 기준 약 1초 분량의 위치 기록을 보관해요.
- 부작용: **"벽 뒤로 숨었는데 맞았다"** 현상, **피커스 어드밴티지**(먼저 튀어나오는 사람이 유리한 현상). Riot은 128틱과 자체 네트워크 경로(Riot Direct)로 이걸 줄이려 했다고 밝혔어요.

```
개념 그림 (내 캐릭터)
입력 1 → 화면에 바로 반영(예측) ──▶ 서버로 전송
입력 2 → 화면에 바로 반영(예측) ──▶ 서버로 전송
            ◀── 서버: "입력 1까지 처리했어, 위치는 (10, 5)"
화면: 위치를 (10, 5)로 맞춤 → 아직 확인 안 된 입력 2를 다시 적용 (보정)
```

### 장르별로 다른 방식
| 장르 | 흔한 방식 |
|---|---|
| **FPS·배틀로얄 (발로란트·배그)** | 서버 권위 + 예측·보정·보간·지연 보상 |
| **MOBA (롤)** | 서버 권위 + 결정론적 시뮬레이션(같은 입력이면 같은 결과). Riot은 롤 게임 서버를 결정론적으로 만드는 데 여러 엔지니어가 거의 1년을 들였다고 공개 |
| **격투 게임** | **롤백 넷코드**(GGPO): 상대 입력을 예측해 바로 진행하고, 틀리면 되감아 다시 계산. 2019년 오픈소스로 공개됨. 핵심 난관은 "완전히 같은 결과가 나오는 결정론" |
| **RTS (스타크래프트류)** | 전통적으로 **결정론적 록스텝**: 모두가 같은 입력을 같은 순서로 실행 |
| **턴제 (오목·카드)** | 웹소켓 + 서버 판정이면 충분 (20장) |

## 5. 통신 방식 — 왜 UDP를 쓰나

| 방식 | 특징 | 게임에서 |
|---|---|---|
| **TCP** | 순서·도착 보장, 하나 잃어버리면 다시 받을 때까지 **뒤에 것도 멈춤** | 로그인·상점·채팅 (백엔드) |
| **UDP** | 빠르지만 잃어버리거나 순서가 바뀔 수 있음 | **실시간 게임 플레이** — 0.1초 전 위치를 다시 받느니 최신 위치를 받는 게 낫기 때문 |
| **웹소켓 / WebRTC** | 브라우저에서 쓰는 실시간 통신 | 웹 게임 (웹소켓은 TCP 기반, WebRTC 데이터 채널은 UDP 비슷하게 사용 가능) |

- 게임 엔진·네트워크 라이브러리는 UDP 위에 **"꼭 필요한 것만 다시 보내기"**(신뢰성 선택), 압축, 암호화를 얹어서 써요.
- **관심 영역(Relevancy)**: 100명 게임에서 모두에게 모든 정보를 보내면 너무 많아요. **내 근처·내가 볼 수 있는 것만** 보내요(에픽은 포트나이트에서 플레이어 근처 액터 위주로 갱신하는 방식을 설명). 이건 **월핵(벽 너머 보기) 방지**에도 도움이 돼요.

## 6. 매치메이킹 — 실력 비슷한 10명 모으기

```
1. 플레이어가 "게임 찾기" → 대기열(큐)에 들어감 (코딩 7장 큐)
2. 매치메이커가 대기열을 계속 훑으며 조건이 맞는 사람끼리 묶음
   - 실력 점수(Elo·MMR, 20장), 지역(핑), 파티 인원, 포지션, 대기 시간
3. 오래 기다릴수록 조건을 조금씩 넓힘 (실력 범위 확대)
4. 팀 구성 완료 → 게임 서버 배정 요청
5. 모두 "수락" → 접속 정보 전달 → 게임 시작
```
- **트레이드오프**: 공정한 매칭(비슷한 실력) ↔ 빠른 매칭(대기 시간 짧게). 사람이 적은 시간·지역엔 이게 가장 어려운 문제예요.
- 경기 후: 결과로 **실력 점수 갱신**, 전적 저장, 보상 지급.

## 7. 게임 서버를 띄우고 관리하기 (오케스트레이션)

| 선택지 | 설명 |
|---|---|
| **Agones** | 쿠버네티스 위에서 전용 게임 서버를 띄우고 늘리는 **오픈소스**. 여러 클라우드에서 같은 방식으로 운영 가능, 대신 운영 부담이 큼 |
| **Amazon GameLift** | AWS의 **관리형** 게임 서버 서비스. 서버 배치·상태 감시·매치메이킹(FlexMatch)까지 제공 |
| **그 밖의 게임 서버 호스팅** | 지역 분산 게임 서버 전문 서비스들, 각 클라우드의 게임 솔루션 |
| **게임 백엔드 서비스(BaaS)** | 로그인·친구·리더보드·저장 등을 빌려 쓰는 서비스 |

### 운영 포인트
- **지역(리전) 분산**: 플레이어 가까운 곳에 서버 (한국 서버, 일본 서버…) → 핑 ↓ (36장)
- **피크 시간 자동 확장**: 저녁·주말에 서버를 늘리고 새벽에 줄여 비용 절약
- **한 판 = 한 프로세스**: 판이 끝나면 정리 → 다음 판을 위해 재사용
- **점검·업데이트**: 새 버전 서버를 띄우고, 진행 중인 판이 끝나면 옛 서버 정리 (20장, 7장 블루-그린)
- 오케스트레이터는 **서버를 띄우는 것까지**예요. 계정·전적·리더보드는 백엔드를 따로 만들어야 해요.

## 8. 치팅 방지와 공정성

| 치팅 | 막는 법 |
|---|---|
| 스피드핵·순간이동 | **서버 권위** — 서버가 이동 속도 검증 |
| 월핵(벽 너머 보기) | **보이는 것만 보내기**(관심 영역) |
| 에임봇 | 클라이언트 안티치트 프로그램, 행동 통계 분석(비정상적으로 정확한 조준) |
| 패킷 조작 | 암호화, 서버 검증 |
| 어뷰징·작업장 | 백엔드에서 이상 거래·패턴 탐지 (35장) |

## 9. 작은 팀이 멀티 게임을 만든다면 — 현실적인 단계

| 단계 | 추천 |
|---|---|
| 1. 턴제·캐주얼 | 웹소켓 + 서버 판정 (20장 오목). 일반 웹 호스팅으로도 가능 |
| 2. 소규모 실시간 (2~8명) | **게임 엔진의 내장 네트워크 기능**(유니티·언리얼·고도 등의 멀티플레이 모듈)이나 실시간 게임 서버 프레임워크 사용 |
| 3. 전용 서버 필요 | 관리형 게임 서버 호스팅으로 시작 (직접 오케스트레이션은 나중에) |
| 4. 대규모 | 매치메이킹·지역 분산·안티치트·데이터 분석 팀 |

> 💡 **처음부터 롤·배그 같은 구조를 만들려 하지 마세요.** 대형 게임사도 수십~수백 명이 몇 년에 걸쳐 만든 구조예요. 작은 게임으로 **서버 권위·예측·보간**을 한 번 직접 구현해 보는 게 가장 좋은 공부예요(가브리엘 감베타의 글에 라이브 데모와 예제 코드가 있어요).

### 직접 실습 순서 (코딩 공부와 연결)
1. 웹소켓으로 **두 브라우저 창에 같은 공이 움직이게** 하기 ([코딩 9장](coding/09-web-development.md))
2. 서버가 공 위치를 계산하고(서버 권위), 클라이언트는 입력만 보내기
3. 일부러 지연(300ms)을 넣어 보고 → **클라이언트 예측** 추가
4. 다른 플레이어 움직임에 **보간** 추가
5. 매칭 대기열(큐) + 방 만들기

---

### 이 장 요약
1. 멀티 게임 = **백엔드 서비스(계정·매칭·상점·전적) + 판마다 뜨는 전용 게임 서버 + 서버를 띄우는 오케스트레이션**.
2. 경쟁 게임은 **서버 권위**가 원칙. 지연은 **클라이언트 예측·서버 보정·엔티티 보간·지연 보상**으로 숨기고, 실시간 통신은 주로 **UDP**.
3. **틱 레이트는 비용**(발로란트 128틱은 엄청난 최적화의 결과), 100명 게임은 **보낼 정보를 줄이는 게** 핵심. 작은 팀은 엔진 내장 기능·관리형 서버부터.
