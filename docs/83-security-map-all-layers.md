# 83. 서비스 보안 전체 지도 — 코드 밖의 모든 층까지

> 보안 필수 항목은 [37장](37-security-must-dos.md), 코드 보안 점검은 [82장](82-ai-code-security-review.md), 어뷰징·핵은 [41장](41-abuse-and-cheat-prevention.md), 로그인·권한은 [65장](65-auth-and-accounts.md), AI 기능 보안은 [67장](67-adding-ai-features.md), 법적 신고는 [10장](10-security-and-law.md)에 있어요. **실제 사고 사례는 [84장](84-security-incident-cases.md)**에 모았어요.

82장까지는 주로 **코드**를 봤어요. 하지만 실제 사고는 **코드 밖**에서 더 많이 나요.
- 2025년 국내 대형 사고들은 **패치 안 한 서버**, **퇴사자가 쓰던 인증키**, **평문으로 저장한 관리자 비밀번호**, **백업 부실**에서 시작했어요.
- 해외 대형 사고들은 **2단계 인증 없는 계정**, **잘못 설정한 클라우드**, **남이 만든 부품(공급망)**에서 시작했어요.

이 장은 서비스를 **10개 층**으로 나눠, 층마다 **무엇이 공격받고, 실제로 어떻게 뚫렸고, 무엇을 하면 되는지**를 정리해요.

> ⚠️ 도구·가격·법 기준은 자주 바뀌어요. 이 장은 2026년 11월 조사 기준이에요. ([참고 자료 모음](sources.md))

## 0. 한 장으로 보는 지도

```
  [사람]  사회공학·피싱·내부자 ────────────────────────────┐
     │                                                     │
  [계정]  관리자·클라우드·도메인·깃허브 계정 ──────────────┤
     │                                                     │
  [도메인·메일]  DNS·서브도메인·메일 위조                  │
     │                                                     │  모든 층에
  [네트워크·서버]  열린 포트·패치·DDoS·관리망 분리          │  ⑩ 감시·로그·
     │                                                     │     사고 대응
  [클라우드·설정]  공개 버킷·과한 권한·메타데이터          │
     │                                                     │
  [데이터베이스]  노출·기본 비밀번호·과한 권한·암호화·백업 │
     │                                                     │
  [애플리케이션 코드]  권한 확인·인젝션·업로드 (82장)      │
     │                                                     │
  [공급망]  라이브러리·CDN 스크립트·CI 도구·외주 ───────────┤
     │                                                     │
  [결제·돈]  카드 스키밍·환불 악용·정산 (39·41장)          │
     │                                                     │
  [단말기]  개발자 노트북·직원 PC·모바일 앱 ───────────────┘
```

**1인 사업자에게 가장 효과 큰 5가지** (84장 사례 대부분을 막았을 것들):
1. **모든 중요 계정에 2단계 인증** — 가능하면 **패스키나 보안 키**처럼 피싱에 강한 방식
2. **패치와 업데이트** — 서버 OS, 라이브러리, 내 노트북까지
3. **비밀 키·비밀번호를 코드·문서·메모에 평문으로 두지 않기** + **퇴사·외주 종료 시 즉시 회수**
4. **데이터베이스·저장소를 인터넷에 열어 두지 않기** + **최소 권한**
5. **오프라인(분리된) 백업 + 복구 연습**

## 1. 공격의 종류 — 기준이 되는 목록

### OWASP Top 10 (웹 애플리케이션, 2025년판)
OWASP가 몇 년마다 발표하는 **웹 서비스 위험 순위**예요. 2025년판은 2025년 11월 발표됐어요(최종본 공개 시점은 자료마다 달라요).

| 순위 | 위험 | 쉬운 뜻 | 관련 장 |
|---|---|---|---|
| A01 | **접근 통제 실패** | 남의 데이터를 볼 수 있음, 권한 없는 기능 실행. (예전의 SSRF도 여기로 합쳐짐) | 65·82 |
| A02 | **보안 설정 오류** (5위→2위) | 기본 비밀번호, 공개 버킷, 디버그 모드 켜 둠, 불필요한 기능 | 이 장 4·5절 |
| A03 | **소프트웨어 공급망 실패** (새로 추가) | 남이 만든 부품·빌드 도구·배포 경로가 오염됨 | 이 장 7절, 79장 |
| — | 그 밖에 | 암호화 실패, 인젝션, 불안전한 설계, 인증 실패, 무결성 실패, 로깅·알림 실패 | 37·65·82 |
| A10 | **예외 상황 처리 실수** (새로 추가) | 오류가 났을 때 내부 정보 노출, 이상한 상태로 계속 동작 | 81장 |

### 서비스 종류별 다른 목록도 있어요
- **OWASP API Security Top 10**: API 서비스용 (60장). 객체별 권한 확인 실패(남의 주문 번호)가 1위였어요.
- **OWASP Mobile Top 10**: 모바일 앱용 (25장). 앱 안에 넣은 키, 안전하지 않은 저장 등.
- **OWASP LLM Top 10**: AI 기능용 (67장). 프롬프트 인젝션 등.

### 공격 종류 사전 (자주 듣는 이름)
| 이름 | 무엇 | 84장 사례 |
|---|---|---|
| **크리덴셜 스터핑** | 다른 곳에서 털린 아이디·비밀번호를 그대로 대입 | GS리테일, 23andMe |
| **피싱·스미싱** | 가짜 메일·문자로 비밀번호·인증 코드 빼내기 | npm 패키지 탈취 |
| **MFA 피로 공격** | 2단계 인증 승인 요청을 계속 보내 지쳐서 누르게 | 우버 |
| **사회공학 (헬프데스크 사칭)** | 직원인 척 전화해 비밀번호·2단계 인증 초기화 요청 | MGM |
| **인포스틸러** | 개인 PC에 몰래 깔려 저장된 비밀번호를 훔치는 악성코드 | 스노우플레이크, 우버 |
| **랜섬웨어** | 데이터를 암호화하고 돈 요구 (요즘은 훔친 뒤 공개 협박까지) | 예스24 |
| **공급망 공격** | 내가 쓰는 부품·도구·CDN을 오염시켜 들어옴 | MOVEit, polyfill.io, npm |
| **내부자·퇴사자** | 권한을 가진 사람(또는 남은 키)이 악용 | 쿠팡 |
| **SSRF** | 서버가 대신 내부 주소에 요청하게 만들기 | 캐피털원 |
| **서브도메인 탈취** | 지운 서비스를 가리키는 DNS 기록을 남이 차지 | (이 장 3절) |
| **DDoS** | 대량 트래픽으로 서비스 마비 | (이 장 4절) |
| **스키밍 (매지카트형)** | 결제 페이지에 몰래 스크립트를 넣어 카드 정보 빼가기 | polyfill.io 유형 |

## 2. 층별 지도 — 사람과 계정

### 사람 (사회공학·내부자)
| 위협 | 대책 |
|---|---|
| 가짜 메일·문자로 로그인 유도 | 링크 대신 **직접 주소를 쳐서** 들어가기, 패스키·보안 키 (피싱에 강함) |
| "IT팀인데요" 전화·메신저 | **본인 확인 절차를 미리 정해 두기**: 비밀번호·2단계 인증 초기화는 영상 통화나 사전 등록 번호로만 |
| 퇴사자·외주 종료 후 권한 남음 | **퇴사 체크리스트**(70장): 계정·키·토큰·공유 폴더 **당일 회수**, 그 사람이 만든 키는 **새로 발급** |
| 직원이 고객 정보 대량 조회 | **최소 권한**(65장), 대량 조회·다운로드 **알림**, 감사 로그(66장) |

### 계정 (가장 중요한 층)
**1인 사업자의 "왕관 보석" 계정 목록** — 이 중 하나만 털려도 전부 털려요.
```
□ 이메일 (모든 비밀번호 재설정이 여기로 옴 — 최우선)
□ 도메인 등록 업체 (34장) — 털리면 사이트·메일이 통째로 넘어감
□ 클라우드·호스팅 (AWS, Vercel, Supabase 등)
□ 깃허브 (코드 + CI 비밀 키)
□ 결제·PG 관리자, 은행
□ 앱스토어 개발자 계정, 광고 계정
□ 비밀번호 관리자
```
| 할 일 | 이유 (84장) |
|---|---|
| **모든 왕관 계정에 2단계 인증**, 가능하면 **패스키·보안 키** | 스노우플레이크 고객사 침해는 **2단계 인증 없는 계정**에 훔친 비밀번호로 들어온 것 |
| **문자(SMS) 인증보다 앱·패스키** | 유심·통신 쪽 사고(SKT·KT)처럼 문자 경로 자체가 위험해질 수 있음 |
| 2단계 인증 승인 요청이 **내가 안 했는데 오면 절대 누르지 않기** + 번호 맞추기 방식 사용 | 우버의 MFA 피로 공격 |
| **비밀번호 재사용 금지**, 비밀번호 관리자 사용 | 크리덴셜 스터핑 |
| 내 서비스 손님 계정도: **로그인 시도 제한·이상 로그인 탐지·유출 비밀번호 차단** | GS리테일·23andMe |
| **복구 수단 정리** (복구 코드 오프라인 보관) | 계정 잠기면 사업이 멈춤 |

## 3. 층별 지도 — 도메인·메일

| 위협 | 무엇 | 대책 |
|---|---|---|
| **도메인 탈취** | 등록 업체 계정이 털리거나 갱신을 놓침 | 등록 업체 2단계 인증, **도메인 잠금(전송 잠금)**, 자동 갱신 (34장) |
| **서브도메인 탈취** | `promo.내도메인`이 **지운 클라우드 서비스**를 계속 가리키면, 남이 그 이름을 다시 만들어 내 주소로 가짜 페이지를 띄움 | 서비스를 지울 때 **DNS 기록도 같이 삭제**, 분기마다 DNS 기록 점검 |
| **메일 위조** | 내 도메인을 사칭해 손님에게 피싱 메일 | **SPF·DKIM·DMARC**, DMARC 정책을 점차 `quarantine`→`reject`로 (30장) |
| **DNS 변경** | 공격자가 DNS를 바꿔 사이트·메일을 가로챔 | DNS 관리 계정 보호, 변경 알림 |

## 4. 층별 지도 — 네트워크·서버

| 위협 | 대책 | 84장 사례 |
|---|---|---|
| **패치 안 된 서버·소프트웨어** | 자동 보안 업데이트, **지원 종료(EOL) OS 쓰지 않기**, 패치 목록 관리 | 롯데카드(7년 묵은 웹로직 취약점), SKT(2016년 경보 취약점 방치), 예스24(지원 종료 OS 보도) |
| **자산 목록에서 빠진 서버** | **모든 서버·서비스 목록**(쓰지 않는 것 포함)을 만들고 안 쓰면 끄기 | 롯데카드: 쓰지 않던 엔진 하나가 패치에서 누락 |
| **열린 포트** | 웹(443)만 열고 DB·관리 포트는 닫기, **관리 접속은 VPN·접속 IP 제한** | — |
| **망이 한 덩어리** | 인터넷에 닿는 서버와 **관리·핵심 서버를 분리**(망 분리), 관리 서버에서 핵심 서버로 가는 길 최소화 | SKT: 인터넷·관리·코어망을 같은 망으로 연결 |
| **관리자 비밀번호를 서버에 평문 저장** | **비밀 관리 도구**(호스팅의 비밀 설정, Vault 등), 평문 파일 금지 | SKT: 핵심 서버 계정 정보가 다른 서버에 평문 저장 |
| **DDoS** | CDN·DDoS 방어 서비스(클라우드플레어 등) 뒤에 두기, 요청 제한 (41장) | — |
| **장비·인증서 재사용** | 기기마다 다른 인증서, 짧은 유효 기간, 분실·회수 관리 | KT: 모든 펨토셀이 같은 인증서, 유효 기간 10년 |

> 💡 1인 사업자라면 **서버를 직접 운영하지 않는 것**(빌더·PaaS, 36장)만으로 이 층의 위험 대부분이 업체 몫이 돼요. 직접 운영한다면 이 표가 필수예요.

## 5. 층별 지도 — 클라우드·설정

OWASP 2025에서 **보안 설정 오류가 2위**로 올라왔어요. 클라우드 사고는 대부분 **해킹 기술보다 설정 실수**예요.

| 위협 | 대책 | 사례 |
|---|---|---|
| **공개된 저장소(버킷)** | 기본은 **비공개**, 공개가 필요한 파일만 별도 버킷, 공개 설정 알림 | Tea 앱: 신분증 사진이 **보안 규칙 없는 Firebase 저장소**에 |
| **과한 권한(IAM)** | 서버·사람마다 **필요한 권한만**, 와일드카드(`*`) 권한 금지 | 캐피털원: 방화벽 역할에 과한 권한 |
| **메타데이터 서비스 악용** | AWS는 **IMDSv2(토큰 필수)** 사용, SSRF 막기 | 캐피털원 |
| **오래된 접근 키** | 키 수명 짧게, **정기 교체**, 안 쓰는 키 삭제 | 스노우플레이크: 2020년 비밀번호가 교체 안 된 채 사용 |
| **루트(최고 관리자) 계정 일상 사용** | 루트는 2단계 인증 걸고 봉인, 일상 작업은 별도 계정 | — |
| **로그 꺼 둠** | 클라우드 감사 로그(CloudTrail 등) 켜기 | — |
| **요금 폭탄 (키 유출 결과)** | 예산 알림·사용량 상한 (68장) | 57장 사례 |

**점검 도구**: 클라우드 회사의 기본 보안 점검(AWS Security Hub·Trusted Advisor 등), 수파베이스 대시보드의 **보안 권고(Security Advisor)**, 오픈소스 **Trivy**(설정 파일·도커 이미지 검사, 82장).

## 6. 층별 지도 — 데이터베이스 (자세히)

데이터베이스는 **손님 정보가 실제로 있는 곳**이라 거의 모든 사고의 마지막 목적지예요.

### 6-1. 위협과 대책 표
| 위협 | 어떻게 뚫리나 | 대책 |
|---|---|---|
| **인터넷에 노출된 DB** | DB 포트(5432·3306·27017 등)를 인터넷에 열어 둠 → 자동 스캔 봇이 찾아 들어와 데이터를 지우고 몸값 요구하는 일이 반복돼 왔어요 | DB는 **사설망에만**, 접속 IP 제한, 관리형 DB 사용 |
| **기본·약한 비밀번호** | 설치 그대로의 관리자 계정 | 긴 무작위 비밀번호, 기본 계정 비활성화 |
| **앱이 최고 관리자 계정으로 접속** | 앱이 뚫리면 DB 전체가 뚫림 | 앱 전용 계정에 **필요한 권한만**(읽기·쓰기 표 제한, 표 삭제 권한 없음) |
| **화면에서 DB로 바로 접근 + 행 단위 규칙 없음** | 수파베이스·파이어베이스 공개 키로 누구나 조회 | **모든 표에 RLS**, 파이어베이스는 **보안 규칙**(59장, Tea 앱·57장 사례) |
| **SQL 인젝션** | 입력값을 쿼리에 그대로 붙임 | **자리 표시자(파라미터 바인딩)** 사용 (37·82장), MOVEit 사례 |
| **암호화 안 된 민감 정보** | DB·백업이 털리면 그대로 노출 | **비밀번호는 해시**(65장), 주민번호·카드번호 등은 **암호화 저장**(법적 의무 있는 항목, 10장), 롯데카드 사례 |
| **전송 중 노출** | DB 연결이 암호화 안 됨 | DB 연결에 **TLS** |
| **백업이 같은 곳에 있음** | 랜섬웨어가 백업까지 암호화 | 3-2-1 백업(8장): **다른 계정·다른 위치·변경 불가(불변) 백업**, 백업 키도 분리 (LastPass 사례) |
| **너무 오래 보관** | 쓸모없는 옛 데이터까지 유출 | 보관 기간 지나면 **파기**(10장), 꼭 필요한 것만 수집 |
| **대량 조회 못 알아챔** | 내부자·키 탈취로 수천만 건 조회 | **조회량 이상 알림**, 감사 로그, 관리자 조회 사유 기록 (쿠팡 사례: 5개월 넘게 몰랐다는 보도) |
| **개발·테스트에 운영 데이터 복사** | 보안이 약한 테스트 환경에서 유출 | 테스트는 **가짜 데이터**, 꼭 필요하면 가명 처리 |
| **로그·분석 도구로 새는 개인정보** | 로그·GA에 이메일·전화가 찍힘 | 로그에서 개인정보 가리기 (68·79장 정규식 예제) |

### 6-2. 데이터베이스 보안 체크리스트
```
접근
□ DB가 인터넷에서 직접 접속되지 않는가 (사설망·IP 제한)
□ 앱 계정은 최소 권한인가 (표 삭제·사용자 관리 권한 없음)
□ 관리자 접속은 2단계 인증·VPN·접속 기록
□ 수파베이스/파이어베이스: 모든 표·저장소에 RLS·보안 규칙

데이터
□ 비밀번호는 해시, 법정 암호화 대상(주민번호·카드·계좌 등)은 암호화
□ 연결은 TLS
□ 꼭 필요한 정보만 수집, 보관 기간 지나면 파기

백업·복구
□ 다른 계정·다른 위치의 백업 + 변경 불가 설정
□ 백업 키는 운영 키와 분리
□ 분기마다 복구 훈련 (8장)

감시
□ 대량 조회·다운로드 알림
□ 관리자 조회 감사 로그 (접속기록 보관 의무, 37장)
□ 운영 데이터를 개발 환경에 복사하지 않음
```

## 12. 내 서비스 위협 지도 그리기 (30분, 선택)

**위협 모델링** = "누가, 어디로, 무엇을 노릴까"를 미리 그려 보는 것이에요. 업계에서는 STRIDE 같은 틀을 쓰는데, 1인 사업자용으로 줄이면:

```
1. 내 서비스의 그림을 그린다: 손님 → 화면 → 서버 → DB / 외부 서비스(결제·메일·AI)
2. 가장 중요한 것 3개에 동그라미: (예) 손님 개인정보, 결제, 관리자 계정
3. 화살표마다 묻는다:
   - 누가 남인 척할 수 있나?          (사칭 → 로그인·2단계 인증)
   - 누가 값을 바꿀 수 있나?          (변조 → 서버 검증·서명)
   - 누가 몰래 볼 수 있나?            (유출 → 권한·암호화)
   - 누가 멈추게 할 수 있나?          (마비 → 요청 제한·백업)
   - 누가 권한을 넘을 수 있나?        (권한 상승 → 최소 권한)
4. 위 10개 층 표에서 해당 대책을 골라 할 일 목록으로
```

> 💡 Claude에게: "내 서비스 구성은 [손님 웹 → Rust 서버 → Supabase DB, 외부: 토스페이먼츠·이메일·Claude API]야. 83장의 10개 층 기준으로 위협 지도를 표로 그려 주고, 1인 사업자가 먼저 해야 할 5가지를 우선순위로 골라 줘. 각각 확인 방법도 알려 줘."

---

### 이 장 요약
1. 사고는 코드 밖에서 더 많이 난다 — **사람·계정·도메인·서버·클라우드·DB·공급망·결제·단말기·감시** 10개 층을 모두 본다.
2. 1인 사업자 핵심 5가지: **피싱에 강한 2단계 인증, 패치, 평문 비밀 금지·퇴사 시 즉시 회수, DB·저장소 비공개와 최소 권한, 분리된 백업과 복구 연습**.
3. 데이터베이스는 **인터넷에 열지 않고, 앱은 최소 권한, RLS·보안 규칙, 민감 정보 암호화, 분리된 백업, 대량 조회 알림**까지 챙긴다. 사례는 84장.
