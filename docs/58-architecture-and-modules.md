# 58. 설계와 모듈화 — 고치기 쉬운 코드 구조

> 원칙 이름(SOLID 등)은 [코딩 11장](coding/11-mastery.md), 파일 나누기 기초는 [코딩 6장](coding/06-intermediate-oop.md)에 있어요. 데이터 설계는 [59장](59-database-design.md), API 설계는 [60장](60-api-design.md)에서 이어져요.

**모듈화** = 프로그램을 **역할이 분명한 작은 덩어리(모듈)**로 나누는 것이에요.

집으로 비유하면 이래요.
- 모듈화가 안 된 코드는 **전선·수도관·가스관이 한 벽 속에 엉켜 있는 집**이에요. 전등 하나 고치려다 수도가 터져요.
- 모듈화된 코드는 **방마다 배선함이 따로 있는 집**이에요. 고칠 곳만 열면 돼요.

57장 실패 사례에서 "AI로 고치려 하자 다른 곳이 계속 고장 났다"는 것이 바로 엉킨 집의 증상이에요.

---

## 1. 왜 설계가 필요한가 — 1인 사업자에게 특히

| 설계가 없으면 | 설계가 있으면 |
|---|---|
| 한 파일이 수천 줄, 어디를 고쳐야 할지 모름 | 파일 이름만 보고 고칠 곳을 찾음 |
| 결제 회사를 바꾸려면 코드 수십 곳 수정 | **한 곳**만 바꿈 |
| 하나 고치면 엉뚱한 곳이 고장 | 고친 모듈 안에서만 영향 |
| AI가 전체를 읽느라 헤매고 실수 | AI에게 "이 폴더만 보고 고쳐"라고 할 수 있음 |
| 외주·직원에게 설명하기 어려움 | 폴더 구조가 곧 설명서 |

> 💡 설계는 거창한 그림이 아니에요. **"무엇을 어디에 둘지"와 "누가 누구를 불러도 되는지"의 규칙**이에요.

---

## 2. 좋은 모듈의 두 가지 기준 — 응집도와 결합도

| 기준 | 뜻 | 좋은 상태 | 비유 |
|---|---|---|---|
| **응집도** | 한 모듈 안의 것들이 **얼마나 같은 일에 모여 있나** | **높을수록** 좋음 | 주방 도구는 주방에 |
| **결합도** | 모듈끼리 **얼마나 서로 엉켜 있나** | **낮을수록** 좋음 | 주방을 고쳐도 욕실은 멀쩡 |

**"응집도는 높게, 결합도는 낮게"** — 설계 원칙 대부분이 이 한 문장을 다르게 말한 것이에요.

결합도가 높은 신호:
- 한 기능을 고치는데 **파일 5개 이상**을 같이 고쳐야 한다
- 다른 모듈의 **내부 변수**를 직접 꺼내 쓴다
- `utils.py`, `common.js` 같은 **잡동사니 파일**이 점점 커진다

---

## 3. 폴더를 나누는 두 가지 방법

### ① 역할별(계층별)로 나누기
```
src/
├── routes/        ← 주소별 입구 (화면·API 요청 받기)
├── services/      ← 업무 규칙 (주문 금액 계산, 재고 확인)
├── repositories/  ← 데이터 저장·조회
└── models/        ← 데이터 모양
```
- 장점: 처음 배우기 쉬움, 작은 프로젝트에 적합
- 단점: "주문" 기능 하나 고치려면 **폴더 4곳**을 돌아다녀야 함

### ② 기능별로 나누기 (추천)
```
src/
├── orders/        ← 주문에 관한 모든 것
│   ├── routes.py
│   ├── service.py
│   └── repository.py
├── products/      ← 상품
├── users/         ← 회원
├── payments/      ← 결제 회사 연동
└── shared/        ← 정말 모두가 쓰는 것만 (날짜·금액 표시 등)
```
- 장점: **"주문"을 고칠 땐 `orders/`만** 보면 됨. 응집도가 높아요.
- 각 기능 폴더 **안에서** 다시 입구·규칙·저장으로 나눠요(①을 작게).

> 💡 실무에서 많이 쓰는 조합: **바깥은 기능별, 안쪽은 역할별.** 이렇게 기능 경계가 분명한 하나의 프로그램을 **모듈러 모놀리스**라고 불러요. 작은 서비스는 여러 서버로 쪼개는 마이크로서비스보다 이쪽이 맞아요([코딩 11장](coding/11-mastery.md#모놀리스-vs-마이크로서비스)).

---

## 4. 세 층으로 나누기 — 입구 · 규칙 · 저장

한 기능 안에서도 역할을 나눠요. 식당으로 비유하면:

| 층 | 식당 | 코드에서 하는 일 | 하지 말 것 |
|---|---|---|---|
| **입구** (route·controller) | 홀 직원: 주문 받기 | 요청을 받아 값 확인 → 규칙 층 호출 → 응답 | 금액 계산, DB 직접 조회 |
| **규칙** (service) | 주방장: 요리 | 업무 규칙: 금액 계산, 재고 확인, 쿠폰 적용 | 화면·HTTP를 알면 안 됨 |
| **저장** (repository) | 창고 담당 | DB 저장·조회 | 업무 판단 |

**의존 방향은 한쪽으로만**: 입구 → 규칙 → 저장. 창고 담당이 홀 직원을 부르지 않아요.

장점:
- 같은 "주문하기" 규칙을 **웹·앱·관리자 화면**이 같이 쓸 수 있어요.
- 규칙 층은 화면 없이 **바로 테스트**할 수 있어요 (50장).

---

## 5. 외부 서비스는 감싸서 쓰기 (갈아 끼우기 쉽게)

결제·이메일·문자·AI API 같은 **바깥 회사 서비스**는 언젠가 바뀌어요(수수료, 장애, 서비스 종료). 그래서 **한 모듈 안에 감싸 두고**, 나머지 코드는 그 모듈만 불러요.

```python
# payments.py — 결제 회사와 이야기하는 부분만 모아 둔 모듈
class FakePayment:
    """테스트용 가짜 결제. 실제 돈이 나가지 않아요."""
    def charge(self, order_id, amount):
        return {"ok": True, "payment_id": f"fake-{order_id}", "amount": amount}

class TossPayment:
    """진짜 결제 회사용. 실제 연동 코드는 이 안에만 둬요."""
    def __init__(self, secret_key):
        self.secret_key = secret_key   # 키는 서버의 환경 변수에서 받아요
    def charge(self, order_id, amount):
        raise NotImplementedError("여기에 결제 회사 API 호출을 넣어요")

# orders.py — 주문 규칙만 아는 모듈. 어떤 결제 회사인지는 몰라요.
def place_order(order_id, items, payment):
    total = sum(price * qty for price, qty in items)
    if total <= 0:
        return {"ok": False, "reason": "주문 금액이 0원이에요"}
    result = payment.charge(order_id, total)
    return {"ok": result["ok"], "total": total, "payment_id": result["payment_id"]}

# main.py — 조립하는 곳. 결제 회사를 바꾸려면 여기 한 줄만 바꿔요.
payment = FakePayment()
print(place_order("A001", [(12900, 2), (3000, 1)], payment))
print(place_order("A002", [], payment))
```

실행 결과 (직접 돌려 확인했어요):
```
{'ok': True, 'total': 28800, 'payment_id': 'fake-A001'}
{'ok': False, 'reason': '주문 금액이 0원이에요'}
```

- `place_order`는 **"charge라는 기능이 있는 무언가"**만 알면 돼요. 토스든 가짜든 상관없어요.
- 테스트할 때는 `FakePayment`로 **실제 돈 없이** 주문 흐름을 확인해요.
- 이게 코딩 11장의 **의존성 역전(D)** 원칙을 실제로 쓴 모습이에요. 업계에서는 **어댑터(adapter)** 또는 **포트와 어댑터** 구조라고도 불러요.

> 실제 결제 연동 순서(금액 검증·웹훅)는 [39장](39-payments-and-settlement.md)을 따르세요. 위 예시는 구조만 보여 줘요.

## 6. 설정과 비밀은 코드 밖에

| 종류 | 예 | 어디에 |
|---|---|---|
| **비밀** | 결제 비밀 키, DB 비밀번호, AI API 키 | 서버의 **환경 변수** / 호스팅의 비밀 설정. `.env`는 Git에 올리지 않기 |
| **환경별 설정** | 개발용·운영용 DB 주소, 테스트 모드 여부 | 환경 변수 |
| **업무 설정** | 무료 배송 기준 금액, 쿠폰 한도 | 설정 파일이나 관리자 화면 (코드 곳곳에 숫자로 박지 않기) |

→ 57장 실패 사례의 첫 원인(화면 코드에 키)이 여기서 막혀요. 37장 보안과 같은 내용이에요.

## 7. 설계 결정을 기록하기 — ADR

**ADR(아키텍처 결정 기록)** = "왜 이렇게 만들었는지"를 짧게 남기는 문서예요. 2011년 마이클 나이가드(Michael Nygard)가 제안한 형식이 가장 널리 쓰여요.

```markdown
# 0003. 결제는 토스페이먼츠로 한다

- 상태: 채택 (2026-11-01)

## 배경
국내 카드·간편결제를 한 번에 붙여야 한다. 1인 운영이라 정산 관리가 쉬워야 한다.

## 결정
토스페이먼츠를 쓰고, 결제 코드는 payments/ 모듈 안에만 둔다.

## 결과
- 좋아지는 점: 연동 문서가 많고 테스트 모드가 있다.
- 나빠지는 점: 해외 카드는 따로 붙여야 한다. 바꿀 땐 payments/만 고치면 된다.
```

- `docs/decisions/` 폴더에 번호 순으로 쌓아요.
- 6개월 뒤의 나, 외주 개발자, **AI**가 "왜 이렇게 했지?"를 바로 알 수 있어요.

## 8. AI로 만들 때 코드가 뭉치지 않게 하는 법

AI는 시키지 않으면 **한 파일에 계속 덧붙이는** 경향이 있어요. 처음부터 구조를 정해 주세요.

### CLAUDE.md에 넣을 구조 규칙 (예시)
```markdown
# 구조 규칙
- 기능별 폴더: src/orders, src/products, src/users, src/payments
- 각 기능 폴더 안: routes(입구) → service(규칙) → repository(저장). 반대 방향 호출 금지
- 결제·이메일·AI API 호출은 각자 모듈 안에서만. 다른 곳에서 직접 부르지 않기
- 비밀 키는 환경 변수로만. 화면 쪽 코드에 절대 넣지 않기
- 파일이 300줄을 넘으면 나누자고 먼저 제안하기
- 설계를 바꾸면 docs/decisions/에 ADR 추가
```
> CLAUDE.md는 **짧을수록** 잘 지켜진다는 경험담이 많아요. 자세한 설명은 `docs/architecture.md` 같은 별도 문서에 두고 "필요할 때 읽어"라고 적어요.

### 요청문 예시 (복사해서 쓰세요)
- **새로 시작할 때**: "코드 쓰기 전에 폴더 구조와 모듈별 책임을 표로 먼저 제안해 줘. 내가 승인하면 그다음에 만들어."
- **기능 추가할 때**: "쿠폰 기능을 추가하고 싶어. 어느 모듈에 넣을지, 기존 모듈 중 무엇을 고쳐야 하는지 먼저 알려 줘."
- **이미 엉킨 코드를 정리할 때**: "동작은 하나도 바꾸지 말고, `app.py`를 기능별 모듈로 나누는 계획을 단계별로 세워 줘. 한 단계씩 하고 매번 테스트를 돌려."
- **점검할 때**: "이 프로젝트에서 다른 모듈의 내부를 직접 건드리는 곳, 결제·외부 API를 여러 곳에서 직접 부르는 곳을 찾아 줘."

### 리팩터링 순서 — 엉킨 코드를 안전하게 나누기
```
1. Git 커밋으로 현재 상태 저장 (6장)
2. 지금 동작을 확인하는 테스트 먼저 (50장) — 최소한 손으로 확인할 목록이라도
3. 한 번에 한 기능만 옮기기 (예: 결제 코드 → payments/)
4. 테스트 → 커밋
5. 다음 기능
```
**동작 바꾸기와 구조 바꾸기를 한 번에 하지 않아요.** 문제가 생기면 무엇 때문인지 알 수 없어요.

## 9. 너무 많이 설계하지 않기

| 과한 설계 | 적당한 설계 |
|---|---|
| 첫날부터 마이크로서비스 10개 | 하나의 프로그램 + 기능별 폴더 |
| 쓸 일 없는 "확장성"을 위한 추상화 | **실제로 바뀔 것**(결제·외부 API)만 감싸기 |
| 모든 파일에 인터페이스 | 두 번째 구현이 생길 때 추가 |
| 설계 문서만 몇 주 | 반나절 정하고 만들면서 고치기 |

코딩 11장의 **YAGNI**(지금 필요 없는 건 만들지 않기)와 **KISS**(단순하게)를 기억하세요.

---

### 이 장 요약
1. 모듈화의 목표는 **응집도는 높게, 결합도는 낮게** — 고칠 곳만 열면 되는 구조.
2. **바깥은 기능별 폴더, 안쪽은 입구 → 규칙 → 저장**. 의존은 한 방향으로만.
3. 결제·외부 API는 **한 모듈에 감싸고**, 비밀은 환경 변수에, 결정은 **ADR**로 남긴다. AI에게는 **구조를 먼저 제안하게** 하고 승인 후 만들게 한다.
