# 65. 회원가입·로그인·권한 만들기

> 보안 기본은 [37장](37-security-must-dos.md), 데이터 설계는 [59장](59-database-design.md), API의 권한 확인은 [60장](60-api-design.md)에 있어요.

회원 기능은 거의 모든 서비스에 필요하지만, **직접 처음부터 만들면 사고가 가장 많이 나는 곳**이에요. 이 장은 "무엇을 직접 하고, 무엇을 맡길지"부터 시작해요.

---

## 1. 결론부터 — 로그인은 직접 만들지 말고 맡기기

| 방법 | 예 | 추천 대상 |
|---|---|---|
| **사이트 빌더의 회원 기능** | 아임웹·카페24·쇼피파이 회원 | 쇼핑몰·소개 사이트 (가장 쉬움) |
| **인증 서비스 (BaaS·인증 전문)** | 수파베이스 Auth, 파이어베이스 Auth, Clerk, Auth0 등 | 직접 개발하는 서비스 |
| **프레임워크의 검증된 인증 라이브러리** | 장고(Django) 기본 인증, NextAuth(Auth.js) 등 | 서버를 직접 운영할 때 |
| ✕ **처음부터 직접 구현** | 비밀번호 저장·세션을 손으로 | 공부용으로만 |

> 💡 비밀번호 저장, 비밀번호 찾기, 로그인 시도 제한, 2단계 인증을 **전부 제대로** 만들기는 어려워요. 이미 많은 서비스가 검증한 도구를 쓰는 게 안전해요. AI에게 "로그인 만들어 줘"라고만 하면 직접 구현해 버릴 수 있으니 **"○○ 인증 서비스를 써서"**라고 지정하세요.

## 2. 로그인 방식 고르기

| 방식 | 장점 | 단점 | 언제 |
|---|---|---|---|
| **이메일 + 비밀번호** | 익숙함 | 비밀번호 관리·찾기 기능 필요, 유출 위험 | 기본 |
| **소셜 로그인** (카카오·네이버·구글·애플) | 가입이 한 번 클릭, 비밀번호 저장 안 함 | 해당 회사 정책을 따라야 함 | **국내 B2C는 카카오·네이버 거의 필수** |
| **이메일 링크 / 인증 코드** | 비밀번호 없음 | 메일이 늦으면 불편 | 가끔 쓰는 서비스 |
| **패스키** | 지문·얼굴로 로그인, 피싱에 강함 | 아직 낯선 손님도 있음 | 추가 선택지로 |
| **휴대폰 본인인증** | 실명·성인 확인 | 건당 비용, 개인정보 부담 | 성인 인증·중복 가입 방지가 꼭 필요할 때 (41장) |

### 소셜 로그인이 동작하는 원리 (OAuth)
```
① 손님이 "카카오로 로그인" 클릭
② 카카오 로그인 화면으로 이동 → 손님이 카카오에 로그인하고 "동의"
③ 카카오가 내 사이트로 "확인 코드"를 들려 보냄
④ 내 서버가 그 코드를 카카오에 보내 "이 사람 누구예요?" 물어봄 (비밀 키 사용 — 서버에서만)
⑤ 카카오가 회원 번호·이메일(동의한 것만)을 알려 줌 → 내 회원으로 연결
```
- 내 사이트는 **손님의 카카오 비밀번호를 절대 보지 않아요.** 이 표준 방식을 **OAuth**라고 해요.
- ④의 **비밀 키는 서버에만** (37장). 화면 코드에 넣으면 57장 실패 사례처럼 돼요.
- **같은 사람이 이메일로도, 카카오로도 가입**하는 경우 계정을 합칠지 미리 정해 두세요.
- 받을 수 있는 정보(이메일, 전화번호 등)는 플랫폼 정책·심사에 따라 달라요. **꼭 필요한 것만** 요청하세요(10장 최소 수집).

## 3. 비밀번호를 직접 다룬다면 — 저장 원칙

비밀번호는 **원래 글자를 저장하지 않고**, 되돌릴 수 없는 값(해시)으로 바꿔 저장해요. 로그인할 때는 입력값을 같은 방식으로 바꿔 **비교만** 해요.

OWASP(웹 보안 비영리 단체) 권장: **느린 전용 방식**(Argon2id 우선, 없으면 scrypt, 기존 시스템은 bcrypt). SHA-256 같은 **빠른 해시는 비밀번호용으로 부적합**해요(공격자가 빨리 대입해 볼 수 있어서).

파이썬 기본 기능(scrypt)으로 원리를 확인해 볼 수 있어요.

```python
import hashlib, hmac, secrets

def hash_password(password):
    salt = secrets.token_bytes(16)                      # 사람마다 다른 무작위 값
    digest = hashlib.scrypt(password.encode(), salt=salt, n=2**14, r=8, p=1)
    return salt.hex() + "$" + digest.hex()              # DB에는 이 문자열만 저장

def check_password(password, stored):
    salt_hex, digest_hex = stored.split("$")
    digest = hashlib.scrypt(password.encode(), salt=bytes.fromhex(salt_hex), n=2**14, r=8, p=1)
    return hmac.compare_digest(digest.hex(), digest_hex)  # 시간 차이로 새지 않게 비교

saved = hash_password("granola!2026")
print("DB에 저장된 값 길이:", len(saved))
print("같은 비밀번호 두 번 저장해도 다름:", hash_password("granola!2026") != saved)
print("맞는 비밀번호:", check_password("granola!2026", saved))
print("틀린 비밀번호:", check_password("granola!2027", saved))
print("로그인 유지용 무작위 토큰 예:", len(secrets.token_urlsafe(32)), "글자")
```

실행 결과 (직접 돌려 확인했어요):
```
DB에 저장된 값 길이: 161
같은 비밀번호 두 번 저장해도 다름: True
맞는 비밀번호: True
틀린 비밀번호: False
로그인 유지용 무작위 토큰 예: 43 글자
```

- **솔트(salt)** = 사람마다 붙이는 무작위 값. 같은 비밀번호도 저장값이 달라져서, 한 명이 뚫려도 다른 사람이 같이 뚫리지 않아요.
- ⚠️ 이건 **원리 이해용**이에요. 실제 서비스는 1절의 검증된 도구를 쓰세요.

## 4. 로그인 상태 유지 — 세션과 토큰

| 방식 | 원리 | 특징 |
|---|---|---|
| **세션 + 쿠키** | 서버가 "입장권 번호"를 기억하고, 브라우저는 쿠키에 번호만 보관 | 로그아웃·강제 로그아웃이 쉬움. 일반 웹사이트에 무난 |
| **토큰(JWT 등)** | 서버가 서명한 "출입증"을 손님이 들고 다님 | 여러 서버·앱에서 쓰기 편함. 대신 **중간에 무효화하기 어려움** → 짧은 유효 시간 + 갱신 토큰 |

쿠키 안전 설정 (AI에게 꼭 요청):
- `HttpOnly` (화면 스크립트가 못 읽게), `Secure` (https에서만), `SameSite=Lax` 이상 (다른 사이트에서 몰래 요청 막기)
- 로그인 토큰을 브라우저 `localStorage`에 넣으면 스크립트 공격(XSS)에 노출되기 쉬워요.

## 5. 회원 기능 체크리스트

| 기능 | 꼭 지킬 것 |
|---|---|
| **가입** | 필수 동의(약관·개인정보)와 **선택 동의(마케팅) 분리**, 미리 체크 금지 (30·48장) |
| **이메일 인증** | 남의 이메일로 가입하는 것 방지 |
| **비밀번호 찾기** | "그런 이메일 없음"이라고 알려 주지 않기 (가입 여부가 새어 나감), 재설정 링크는 **짧은 유효 시간·1회용** |
| **로그인 시도 제한** | 5~10번 틀리면 잠시 막기 또는 추가 확인 (41장 계정 탈취) |
| **2단계 인증** | 최소한 **관리자 계정은 필수** (37장) |
| **새 기기 로그인 알림** | 계정 탈취를 손님이 빨리 알 수 있게 |
| **회원 정보 수정** | 이메일·비밀번호 변경 시 **현재 비밀번호 다시 확인** |
| **회원 탈퇴** | **가입만큼 쉽게** (다크 패턴 금지, 48장). 개인정보는 파기, 법적 보관 의무 기록(거래 기록 등)만 분리 보관 (10장) |
| **장기 미사용 계정** | 오래 안 쓴 계정 처리 방침을 개인정보처리방침에 (법 기준은 10장·공식 안내 확인) |
| **만 14세 미만** | 가입 받으려면 법정대리인 동의 필요 → 받지 않을 거면 가입 때 확인 (10장) |

## 6. 권한 — 누가 무엇을 할 수 있나

**로그인(인증)** = "누구인가" 확인 / **권한(인가)** = "이 사람이 이걸 해도 되나" 확인. 사고는 대부분 **권한 쪽**에서 나요.

### 역할(Role) 정하기 예
| 역할 | 할 수 있는 것 |
|---|---|
| 손님 | 내 주문·내 정보만 |
| 판매자 (마켓플레이스) | 내 상품·내 주문만 |
| 상담 직원 | 주문 조회·환불 요청 (환불 승인 ✕, 회원 전체 다운로드 ✕) |
| 관리자 | 대부분 |
| 대표 | 전부 + 권한 변경 |

### 반드시 서버에서 확인
- 화면에서 버튼을 숨기는 건 **편의일 뿐 보안이 아니에요.** 주소를 직접 쳐서 요청할 수 있어요.
- 모든 요청에서: **로그인했나 → 이 역할이 이 행동을 해도 되나 → 이 데이터가 이 사람 것인가**.
- 마지막 단계(남의 데이터 접근)를 빠뜨리는 실수가 가장 흔해요. 50장 "남의 주문 번호 넣어 보기" 테스트로 꼭 확인하세요. 수파베이스를 쓰면 RLS로 DB에서도 한 번 더 막아요(59장).
- 직원 권한은 **필요한 만큼만**(최소 권한), 퇴사하면 **바로 회수**(10장).

> 💡 Claude에게: "이 프로젝트의 모든 API와 화면을 표로 정리하고, 각각 ① 로그인 필요 여부 ② 허용 역할 ③ 본인 데이터 확인 여부를 표시해 줘. 빠진 곳은 고쳐 줘."

---

### 이 장 요약
1. 로그인은 **빌더·인증 서비스·검증된 라이브러리**에 맡긴다. 국내 B2C는 **카카오·네이버 소셜 로그인**을 고려.
2. 비밀번호는 **느린 전용 해시 + 솔트**로, 로그인 유지 쿠키는 **HttpOnly·Secure·SameSite**.
3. **인증(누구)과 권한(무엇을)**을 나누고, 모든 요청에서 **서버가 본인 데이터인지** 확인한다. 탈퇴는 가입만큼 쉽게.
