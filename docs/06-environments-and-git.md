# 06. 개발 환경과 버전 관리

> ❓ **질문: "업데이트하거나 고칠 때, 백업 폴더를 따로 만들어서 거기서 하나요?"**
>
> ✅ **답: 생각은 맞는데, 현업은 "폴더 복사" 대신 두 가지 장치를 씁니다.**
> 1. **환경을 나눈다** — 실제 사이트와 똑같은 "연습용 사이트"를 따로 두고 거기서 먼저 고친다.
> 2. **버전 관리(Git)를 쓴다** — 폴더를 복사하는 대신, 바뀐 기록을 전부 저장해서 언제든 예전으로 되돌린다.
>
> 그리고 **손님 데이터(DB)** 는 이것과 별도로 백업합니다(8장).

---

## 1. 왜 "폴더 복사 백업"만으로는 부족할까?

옛날 방식(그리고 많은 초보자가 하는 방식):

```
myshop/
myshop_backup/
myshop_backup_0315/
myshop_최종/
myshop_최종_진짜최종/
myshop_최종_진짜최종_수정2/
```

문제점
- 어느 게 최신인지, 무엇이 바뀌었는지 알 수 없다.
- 두 사람이 동시에 고치면 서로 덮어쓴다.
- **손님 주문 데이터(DB)는 이 폴더에 없다.**
- 실제 사이트를 직접 고치다 실수하면, 그 순간 손님이 오류 화면을 본다.

---

## 2. 해결책 ① — 환경을 3개로 나눈다

| 환경 | 별명 | 누가 보나 | 하는 일 |
|---|---|---|---|
| **로컬(개발)** | 연습장 | 나만 | 마음껏 고치고 부숴 보기 |
| **스테이징** | 리허설 무대 | 나와 팀(비공개 주소) | 운영과 똑같은 조건에서 최종 확인 |
| **운영(프로덕션)** | 실제 무대 | 진짜 손님 | **여기서는 직접 고치지 않는다** |

```
[로컬에서 수정] ──테스트 OK──▶ [스테이징에서 확인] ──문제 없음──▶ [운영에 배포]
                                                         문제 생기면 ◀── 롤백(되돌리기)
```

**황금률: 운영 사이트를 직접 고치지 않는다.**
→ 이게 질문하신 "백업본으로 작업한다"의 현업 버전이에요. 다만 "백업본"이 아니라 **"똑같이 생긴 연습용 사이트"** 입니다.

### 스테이징을 만들 때 주의
- 스테이징에서 **진짜 결제**나 **진짜 손님에게 문자**가 나가지 않게 테스트 모드로 설정 (PG사는 보통 "테스트 키"를 따로 줍니다).
- 운영 DB를 복사해 쓸 경우 **개인정보(이름·전화번호)는 가짜로 바꾸기**(마스킹).
- 검색 엔진에 노출되지 않게 비밀번호를 걸어 두기.

### 빌더(카페24, 아임웹 등)를 쓴다면?
- 대부분 **"디자인 미리보기/테스트 스킨"** 기능이 있습니다. 새 디자인은 복사본 스킨에서 고치고, 확인 후 "대표 디자인으로 적용"하는 방식 = 스테이징과 같은 개념.
- 바꾸기 전 **기존 스킨을 복사해 두는 것**이 곧 백업.

## 3. 해결책 ② — 버전 관리(Git)

**Git** = 파일이 바뀔 때마다 "언제, 누가, 무엇을, 왜" 바꿨는지 기록하는 **타임머신**.

| 폴더 복사 방식 | Git 방식 |
|---|---|
| `myshop_최종_진짜최종` | 하나의 폴더 + 변경 기록 전부 |
| 무엇이 바뀌었는지 모름 | 줄 단위로 바뀐 부분이 보임 |
| 되돌리려면 폴더 바꿔치기 | 명령 하나로 원하는 시점으로 |
| 동시에 고치면 충돌 | 브랜치로 따로 작업 후 합침 |

### Git 기본 단어 (게임 세이브로 비유)

| Git 단어 | 게임 비유 |
|---|---|
| **저장소(Repository)** | 게임 세이브 파일 묶음 |
| **커밋(Commit)** | 세이브 포인트에서 저장 ("보스 잡기 직전") |
| **브랜치(Branch)** | 세이브를 복사해서 "다른 선택지"를 시험해 보기 |
| **머지(Merge)** | 시험해 본 선택지가 좋아서 본 세이브에 합치기 |
| **되돌리기(Revert)** | 이전 세이브 포인트로 돌아가기 |
| **GitHub** | 세이브 파일을 인터넷 금고에 올려 두는 곳 (컴퓨터가 고장 나도 안전) |

### 실제 작업 흐름 (가장 흔한 방식)

```
main  ●────●────────────●────▶  (= 운영 사이트에 나가 있는 코드)
            \          /
feature      ●───●───●          (= "장바구니 버튼 색 바꾸기" 작업 갈래)
```

1. `main`(운영용 원본)에서 새 **브랜치**를 만든다. 예: `fix-cart-button`
2. 브랜치에서 고치고 **커밋**한다.
3. 스테이징에 올려서 확인한다.
4. 괜찮으면 `main`에 **머지**한다 → 운영에 배포.
5. 문제가 생기면 이전 커밋으로 **되돌린다**.

### 좋은 커밋 메시지 예
- ❌ `수정`, `asdf`, `최종`
- ✅ `장바구니 버튼을 주황색으로 변경 (모바일 클릭률 개선)`

---

## 4. 설정값과 비밀번호는 코드와 분리

- 결제 키, DB 비밀번호 같은 **비밀 정보는 코드에 직접 쓰지 않습니다.** 환경마다 다른 "환경 변수"로 따로 넣어요.
- 실수로 GitHub에 비밀번호를 올리면 **몇 분 안에 자동 스캔 봇에게 털릴 수 있습니다.** → 바로 키를 새로 발급(교체)하세요.

---

### 이 장 요약
1. 운영 사이트는 **직접 고치지 않는다**: 로컬 → 스테이징 → 운영.
2. "백업 폴더 복사" 대신 **Git**으로 모든 변경을 기록하고, 언제든 되돌린다.
3. Git은 **코드**를 지킨다. **손님 데이터(DB)** 는 8장의 백업으로 따로 지킨다.
