# 50. 테스트 실전 — 직접 막 눌러 보는 것부터 자동 테스트까지

"테스트" = 손님보다 **내가 먼저** 문제를 찾는 일이에요.
[코딩 8장](coding/08-developer-tools.md)에서 자동 테스트 코드를 봤다면, 이 장은 **출시 전·업데이트 전에 실제로 무엇을, 어떻게 확인하나** 예요.

> 부하 테스트 결과로 용량을 계획하는 법은 [81장](81-optimization-and-stabilization.md)에 있어요.

> ([참고 자료 모음](sources.md))

## 1. 테스트의 종류 한눈에

| 종류 | 누가 | 무엇을 | 언제 |
|---|---|---|---|
| **직접 막 눌러 보기 (탐색 테스트)** | 나 | 이상하게 써 보며 깨뜨리기 | 기능 하나 만들 때마다 |
| **시나리오 테스트** | 나·팀 | 정해진 흐름(가입→구매→환불) 끝까지 | 출시·업데이트 전 |
| **기기·브라우저 테스트** | 나 | 아이폰·안드로이드·PC, 크롬·사파리 | 출시 전 |
| **사용성 테스트** | 손님 5명 | 헷갈리는 곳 찾기 (48장) | 화면 만든 뒤 |
| **베타 테스트** | 소수의 실제 손님 | 실제 환경에서 써 보기 | 정식 출시 전 |
| **자동 테스트** | 코드 | 단위·통합·E2E (코딩 8장) | 코드 바꿀 때마다 자동 |
| **부하 테스트** | 도구 | 사람이 몰려도 버티나 | 큰 이벤트·광고 전 |
| **보안 점검** | 나·도구 | 37장 체크리스트 | 출시 전·정기 |

## 2. 직접 막 눌러 보기 — "깨뜨리는 사람"이 되기

만든 사람은 "정상적인 사용"만 해 봐요. 손님은 **예상 못 한 행동**을 해요. 일부러 이상하게 써 보세요.

### 입력칸에 넣어 볼 것
| 넣어 볼 값 | 확인 |
|---|---|
| 빈칸 그대로 제출 | 친절한 안내가 나오나 |
| 아주 긴 글 (1,000자) | 화면이 깨지나 |
| 이모지·특수문자 😀 `<script>` `'` | 깨지거나 이상하게 실행되나 (XSS·인젝션, 37장) |
| 0, 음수, 소수점 (수량 -1, 가격 0.5) | 계산이 이상해지나 |
| 공백만 "   " | 이름이 빈칸으로 저장되나 |
| 이메일 형식 아닌 값 | 막히나 |

### 행동으로 해 볼 것
| 행동 | 확인 |
|---|---|
| 버튼 **빠르게 두 번** 클릭 | 주문·결제가 두 번 되나 (39장 멱등성) |
| 결제 중 **뒤로 가기·새로고침** | 주문 상태가 꼬이나 |
| 결제창에서 **취소** | "결제 실패"로 잘 돌아오나 |
| 로그인 안 한 상태로 마이페이지 주소 직접 입력 | 막히나 |
| **남의 주문 번호**로 주소 바꿔 보기 | 보이면 큰일 (37장 A01) |
| 장바구니에 담고 **며칠 뒤** 결제 (가격·재고 바뀜) | 바뀐 가격으로 처리되나 |
| 인터넷 끊고 버튼 누르기 (개발자 도구로 오프라인) | 안내가 나오나 |
| 휴대폰 **가로 화면**, 글자 크게 설정 | 깨지나 |
| 탭 두 개에서 같은 쿠폰 동시 사용 | 두 번 적용되나 (41장) |

## 4. 버그를 기록하는 법

혼자라도 버그는 **목록으로** 남겨요 (깃허브 이슈, 노션, 엑셀).

```
제목: [결제] 아이폰 사파리에서 결제 완료 후 빈 화면
재현 순서: 1) 상품 담기 2) 카카오페이 선택 3) 결제 완료
기대 결과: 주문 완료 페이지
실제 결과: 흰 화면, 새로고침하면 주문 완료 페이지 보임
환경: 아이폰 15, iOS ○○, 사파리
심각도: 높음 (결제 직후라 손님 불안)
첨부: 화면 녹화
```
- **재현 순서**가 가장 중요해요. AI(49장)나 개발자에게 넘길 때도 이 형식 그대로.
- 심각도는 9장 장애 등급(1급·2급·3급)과 같은 기준으로.

## 5. 베타 테스트 — 진짜 손님에게 먼저

| 단계 | 내용 |
|---|---|
| 모집 | 대기자 명단(42장)·지인·커뮤니티에서 10~50명 |
| 안내 | "베타라서 불편할 수 있어요, 의견 주시면 ○○ 드려요" |
| 수집 | 피드백 폼, 짧은 인터뷰, 사용 데이터(GA4) |
| 기간 | 1~4주 |
| 정리 | 버그 목록 + "매우 실망" 질문(42장 40% 테스트) |
| 앱이라면 | 마켓의 베타 테스트 기능 (25장) |

## 6. 부하 테스트 — 사람이 몰려도 버티나

- 광고·방송 노출·한정판 판매 전에 해 봐요.
- **k6, JMeter, Locust** 같은 도구로 가짜 사용자 수백~수천 명이 동시에 접속하게 만들어 봐요.
- 확인: 응답 시간, 오류율, 서버 CPU·DB 사용량 (9장 모니터링)
- ⚠️ **반드시 내 서버(가능하면 스테이징)** 에만. 남의 사이트에 하면 **공격(DDoS)** 이 돼요. 호스팅 약관에 부하 테스트 규칙이 있는지도 확인.
- 빌더 사용자는 업체가 처리하지만, 큰 이벤트 전엔 업체에 미리 알리면 좋아요.

## 7. 자동 테스트를 어디까지 쓸까 (1인 개발자 기준)

| 우선순위 | 자동 테스트 대상 |
|---|---|
| 1 | **돈 계산**: 가격·할인·쿠폰·배송비·환불 금액 |
| 2 | **권한**: 남의 데이터 접근 차단 |
| 3 | **결제 흐름**: 금액 검증, 중복 승인 방지 (39장) |
| 4 | 핵심 시나리오 E2E 1~2개 (가입 → 구매) |
| 5 | 버그를 고칠 때마다 **그 버그를 잡는 테스트** 추가 |

- AI에게 "이 함수의 테스트를 만들어 줘, 경계값(0, 음수, 최대값) 포함해서"라고 요청하고, **테스트가 실제로 실패도 할 수 있는지** 확인 (49장).
- 테스트는 **배포 전 자동 실행**(CI, 7장).

---

## 8. 업데이트할 때마다 — 회귀 테스트

**회귀 테스트** = 새 기능을 넣었더니 **예전에 되던 게 고장 난 건 아닌지** 확인.
- 3절 시나리오 중 핵심(가입·결제·주문 확인)은 **업데이트마다** 다시
- 자동 테스트가 이걸 대신해 주는 게 가장 큰 가치

---

### 이 장 요약
1. **직접 이상하게 써 보기**(빈칸·두 번 클릭·뒤로 가기·남의 주문 번호)로 손님보다 먼저 깨뜨린다.
2. 출시 전 **기기별 시나리오 표**, 버그는 **재현 순서**와 함께 기록, 정식 출시 전 **베타**.
3. 자동 테스트는 **돈 계산·권한·결제**부터, 큰 이벤트 전엔 **내 서버에만 부하 테스트**.
