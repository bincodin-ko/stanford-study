# 82. AI 코드 보안 점검 — 도구·AI·오픈소스로 찾고, 테스트로 고치기

> 보안 필수 항목은 [37장](37-security-must-dos.md), AI로 개발하는 법은 [49장](49-building-with-ai.md), 의존성 관리는 [79장](79-regex-docker-dependencies.md), AI 기능의 보안(프롬프트 인젝션)은 [67장](67-adding-ai-features.md), 실패 사례는 [57장](57-vibe-coding-money-cases.md)에 있어요.

AI로 코드를 빨리 만들수록 **보안 점검도 자동으로** 돌아가야 해요. 57장에서 본 것처럼, AI로만 만든 서비스는 비밀 키 노출·권한 확인 누락으로 며칠 만에 무너지기도 했어요.

## 1. 원칙 — 4겹으로, AI 혼자 맡기지 않기

| 겹 | 잘하는 것 | 못하는 것 |
|---|---|---|
| **① 자동 도구** (정적 분석·비밀 키·라이브러리 검사) | 정해진 패턴을 **빠르고 정확하게**, 매번 똑같이 | 맥락 이해 ("이 사람이 이 주문을 봐도 되나?") |
| **② AI 리뷰** | **논리 취약점**: 권한 확인 누락, 금액 조작, 남의 데이터 접근 | 놓치기도 하고, **없는 문제를 지어내기도** 함 |
| **③ 실제로 공격해 보기** (동적 검사) | 실행 중인 사이트의 실제 동작 | 코드 속 원인은 모름 |
| **④ 고치기 + 테스트 + 사람 승인** | 고친 게 맞는지, 다시 생기지 않는지 보장 | — |

### AI 탐지 능력에 대한 냉정한 사실
- 코드 언어 모델의 취약점 탐지를 엄격하게 평가한 연구(PrimeVul, ICSE 2025)에 따르면, 기존 데이터셋에서 F1 68%였던 70억 파라미터 모델이 **현실적인 평가에서는 3%**로 떨어졌고, GPT-4 같은 큰 모델도 **가장 엄격한 조건에서는 무작위 추측과 비슷**했다고 해요.
- 그래서 **"AI가 괜찮다고 했으니 안전"은 틀린 생각**이에요. AI 리뷰는 **사람 리뷰를 보조하는 두 번째 눈**으로 쓰고, 확실한 것은 **도구와 테스트**로 잡아요.

### 깃허브의 코드 분석기 — CodeQL 자세히

**CodeQL** = 깃허브가 만든 **코드 속 보안 취약점 자동 탐지기**예요. 위 표의 다른 검사기는 "이 줄에 위험한 모양이 있나"를 보지만, CodeQL은 **데이터가 어디서 와서 어디로 흘러가는지**를 따라가요.

```
① 코드를 분석해 "코드 데이터베이스"로 만듦
   (어떤 함수가 무엇을 부르고, 어떤 값이 어디로 흘러가는지)
② 미리 만들어진 보안 질문(쿼리) 수백 개를 던짐
   예) "손님이 입력한 값이 → 검사 없이 → DB 쿼리에 들어가는 길이 있나?"  → SQL 인젝션
③ 찾은 길을 깃허브 화면에 표시
   "이 파일 42번째 줄의 입력이 → 87번째 줄의 쿼리로 흘러감"
```

- **여러 파일에 걸친 취약점**도 값의 흐름으로 찾아요. 단순 검사기가 놓치는 부분이에요.
- 깃허브 저장소 설정 → **Code security → Code scanning → 기본 설정(Default setup)**을 켜면, 언어를 알아서 감지하고 코드를 올릴 때마다 자동 검사해요. 결과는 **Security 탭**과 **PR 댓글**로 와요.
- **Copilot Autofix**: 찾은 취약점의 **수정 코드를 AI가 제안**해요. 4절의 "AI가 PR로 고치고 사람이 승인" 흐름을 깃허브가 기본 기능으로 해 주는 셈이에요.
- **Rust 지원**: 2025년 10월부터 **정식 지원**. 기본 설정에서 **빌드 없이** 검사하고, 쿠키를 Secure 표시 없이 만드는 코드(`rust/insecure-cookie`) 같은 Rust 전용 규칙도 생겼어요(65장 쿠키 설정).

## 4. 고치는 법 — "발견 → 수정 PR → 테스트 → 승인"

```
1. 발견: 도구·AI가 찾은 문제를 목록으로 (심각도·위치·재현 방법)
2. 진짜인지 확인: 실제로 공격 경로가 있나? (가짜 경보면 이유를 적고 예외 처리)
3. 우선순위: 비밀 키 노출 > 남의 데이터·결제 > 인젝션 > 나머지
4. 수정 PR: 문제 하나당 PR 하나, AI에게 맡겨도 됨
5. 테스트 추가: "이 공격이 막히는지" 확인하는 테스트를 같이 (아래 예)
6. CI 통과 + 내가 읽고 승인 → 반영
7. 비밀 키 노출이었다면: 키 즉시 교체 (Git 기록에서 지워도 이미 퍼졌다고 가정, 37장)
```

### 예: AI가 만든 "남의 주문 보기" 취약점과 그걸 막는 테스트

```python
ORDERS = {
    101: {"owner": "kim", "item": "그래놀라", "address": "서울시 ..."},
    102: {"owner": "lee", "item": "요거트", "address": "부산시 ..."},
}

class NotFound(Exception):
    pass

# ✕ AI가 흔히 만드는 코드: 로그인만 확인하고 "누구 주문인지"는 확인 안 함
def get_order_vulnerable(current_user, order_id):
    if current_user is None:
        raise PermissionError("로그인 필요")
    return ORDERS[order_id]

# ○ 고친 코드: 본인 주문이 아니면 "없는 주문"처럼 응답 (존재 여부도 숨김, 60장)
def get_order(current_user, order_id):
    if current_user is None:
        raise PermissionError("로그인 필요")
    order = ORDERS.get(order_id)
    if order is None or order["owner"] != current_user:
        raise NotFound()
    return order

# 이 취약점이 다시 생기지 않게 막는 테스트 (고칠 때 꼭 같이 추가)
def test_cannot_read_someone_elses_order(fn):
    try:
        fn("kim", 102)               # kim이 lee의 주문을 열어 봄
        return "✕ 실패: 남의 주문(주소 포함)이 보여요"
    except NotFound:
        return "○ 통과: 남의 주문은 없는 것처럼 보여요"

def test_can_read_own_order(fn):
    return "○ 통과: 내 주문은 보여요" if fn("kim", 101)["item"] == "그래놀라" else "✕ 실패"

for name, fn in [("고치기 전", get_order_vulnerable), ("고친 뒤", get_order)]:
    print(name, "|", test_cannot_read_someone_elses_order(fn), "|", test_can_read_own_order(fn))
```

실행 결과 (직접 돌려 확인했어요):
```
고치기 전 | ✕ 실패: 남의 주문(주소 포함)이 보여요 | ○ 통과: 내 주문은 보여요
고친 뒤 | ○ 통과: 남의 주문은 없는 것처럼 보여요 | ○ 통과: 내 주문은 보여요
```
→ "고치기 전"에서 **실패하는 테스트**를 먼저 만들고, 고친 뒤 **통과**하는 걸 확인해요. 이 테스트가 CI에 남아 있으면, 나중에 AI가 코드를 다시 고치다 같은 실수를 해도 바로 걸려요.

### AI에게 고치게 할 때의 요청문
> "보안 점검 결과를 줄게. ① 각 항목이 실제로 공격 가능한지 공격 경로를 설명하고, 아니면 가짜 경보라고 해 줘. ② 진짜인 것은 심각도 순으로, 하나씩 따로 고쳐 줘. ③ 고칠 때마다 **그 공격이 막히는지 확인하는 테스트**를 먼저 추가하고, 고치기 전엔 실패·고친 뒤엔 통과하는 걸 보여 줘. ④ 다른 기능은 바꾸지 마."

## 5. (선택) 침투 테스트 — 내 서비스를 공격자처럼 찔러 보기

앞의 ③ "실제로 공격해 보기"를 더 넓힌 거예요. **내가 소유한 내 서비스**를, **스테이징에서**, 공격자가 쓰는 도구로 직접 두드려 보는 거예요. 업계에서는 **침투 테스트(모의 해킹, pentest)**라고 해요. 합법이고 표준 방법이에요.

> 🚨 **먼저, 반드시 지킬 선 (안 지키면 범죄예요)**
> - **내가 소유했거나, 서면 허가를 받은 대상에만.** 남의 서비스·남이 만든 사이트·공용 서버에 돌리면 **정보통신망법 위반**이에요(10장). "되나 궁금해서"도 안 돼요.
> - **운영 서버 말고 스테이징에.** 공격 테스트는 장애·데이터 손상을 일으킬 수 있어요(7장 환경 분리).
> - **범위를 미리 정해서.** 어떤 주소·어떤 기능까지 테스트할지 적어 두고 그 안에서만.
> - 클라우드·호스팅을 쓰면 **업체 약관**도 확인하세요. 침투 테스트를 미리 알려야 하는 곳이 있어요.

### 쓸 수 있는 오픈소스 (내 것에만)
| 하는 일 | 도구 | 비고 |
|---|---|---|
| 웹 취약점 자동 스캔 | **OWASP ZAP** (Apache-2.0) | 로그인 후 영역까지 (인증 스캔). CI에도 넣을 수 있음 |
| 알려진 취약점 빠른 확인 | **Nuclei** | 템플릿(YAML) 기반. ZAP과 함께 쓰면 좋음 |
| 서버에 열린 문(포트) 확인 | **Nmap** | 안 쓰는 포트가 열려 있는지 |
| 웹 서버 설정 실수 | **Nikto** | 흔한 설정 문제 |
| 취약점이 진짜 뚫리는지 검증 | **Metasploit Framework** | 찾은 취약점을 재현해 확인 |
| 위 도구 모음 | **Kali Linux** | 침투 테스트용 리눅스 배포판 |
| 로그인 제한이 실제로 막는지 | 비밀번호 추측 도구 | **내 테스트 계정으로만**, 41장 로그인 제한 확인용 |

### 1인 사업자에게 현실적인 순서
```
1. 스테이징을 운영과 똑같이 만들기 (가짜 데이터로)
2. ZAP 인증 스캔 1회 (로그인 후 화면까지)
3. 50장 "남의 데이터 넣어 보기"를 Nuclei·수동으로 더 넓게
4. 나온 문제를 4절 흐름으로 고치고 테스트 추가
5. 커지면: 전문 업체에 모의 해킹 의뢰 (B2B·투자·인증 때 요구되기도)
```

> 💡 **"공격 코드를 더 잘 만드는 것"이 목적이 아니에요.** 목적은 **내 구멍을 먼저 찾아 막는 것**이에요. 그래서 안전장치를 푼 모델 같은 건 쓰지 않아요 — 내 서비스 보안에 도움이 안 되고, 법·약관 위반 위험만 커져요. 위 정식 도구로 충분하고 더 잘 돼요.

> ⚠️ 도구 사용법을 AI에게 물어보는 건 괜찮지만, **대상은 늘 내 스테이징**이어야 해요. "이 주소를 공격해 줘" 같은 요청은 그 주소가 내 것이 아닐 수 있어 위험해요.

## 6. 내 프로젝트에 넣는 순서 (1인 사업자 버전)

| 단계 | 할 일 | 비용 |
|---|---|---|
| **오늘** | 언어 린터를 "경고도 실패"로, `.env`를 Git 제외, 의존성 검사(`cargo audit`/`npm audit`) 한 번 실행 | 0원 |
| **첫 주** | CI에 **비밀 키 검사(Gitleaks) + 의존성 검사**, 매주 자동 실행 | 0원 |
| **출시 전** | AI 보안 리뷰(`/security-review` 또는 액션) 한 번 + **남의 데이터·결제 테스트**(50장) + 스테이징에 **ZAP 기본 스캔** + 37장 표 | AI 사용료 약간 |
| **운영 중** | PR마다 AI 리뷰(내 PR만), 매주 의존성 알림 처리, 분기마다 37장 다시 | 소액 |
| **커지면** | Semgrep 규칙 추가, 외부 보안 점검(모의 해킹) 의뢰, 버그 바운티 | 유료 |

> 💡 실제 예: 이 교재로 만드는 앱 "한 바퀴"(80장)는 1주차에 **보안 헤더 추가, 경로 조작 차단 테스트, CI 보안 워크플로(cargo audit·Gitleaks·Claude 리뷰)**를 넣었어요.

---

### 이 장 요약
1. 보안 점검은 **도구(정확) + AI(맥락) + 실제 공격 + 테스트·승인**의 4겹. 연구 결과상 **AI 혼자는 믿을 수 없다**.
2. 무료 오픈소스로 시작: **Semgrep·언어 린터, Gitleaks, cargo/npm/pip audit·Trivy·OSV-Scanner, OWASP ZAP, CodeShield**. 허깅페이스 모델(Foundation-Sec-8B 등)은 코드를 밖으로 못 보낼 때의 선택지 — 라이선스 확인.
3. 고칠 때는 **문제 하나당 PR 하나 + 그 공격을 막는 테스트**를 먼저, 비밀 키 노출이면 **즉시 교체**.
