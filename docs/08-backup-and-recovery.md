# 08. 백업과 복구

> **백업은 "복구해 봤을 때" 비로소 백업입니다.**
> 한 번도 되살려 보지 않은 백업은 "있다고 믿는 파일"일 뿐이에요.

---

## 1. 무엇을 백업하나 — 5장의 "세 덩어리" + α

| 대상 | 예 | 백업 방법 | 얼마나 자주 |
|---|---|---|---|
| **코드** | 프로그램, 디자인 파일 | Git + GitHub (6장) | 고칠 때마다 커밋 |
| **데이터베이스** | 회원, 주문, 결제 | DB 자동 백업(덤프/스냅샷) | **최소 하루 1번**, 주문 많으면 더 자주 |
| **업로드 파일** | 상품 사진, 첨부 파일 | 스토리지 복제·백업 | 하루 1번 또는 실시간 복제 |
| **설정값** | 도메인 DNS 설정, 환경 변수, 결제 설정 | 문서로 기록 + 비밀번호 관리자 | 바꿀 때마다 |
| **외부 서비스 데이터** | 빌더 쇼핑몰 상품 목록, 고객 명단 | 엑셀(CSV) 내보내기 | 주 1번 |

> **덤프(Dump)** = DB 내용을 파일 하나로 쏟아내 저장하는 것.
> **CSV** = 엑셀에서 열 수 있는 표 파일.

---

## 2. 얼마나 잃어도 되나 — RPO와 RTO

| 용어 | 질문 | 예 |
|---|---|---|
| **RPO** (복구 시점 목표) | "사고가 나면 **최대 몇 시간 치 데이터**를 잃어도 괜찮나?" | 하루 1번 새벽 백업 → 최악의 경우 하루 치 주문이 사라짐 |
| **RTO** (복구 시간 목표) | "사고 후 **몇 시간 안에** 사이트를 살려야 하나?" | "2시간 안에 복구" |

- 블로그: RPO 1일, RTO 1일이어도 괜찮음.
- 쇼핑몰: 주문이 사라지면 큰일 → RPO 1시간 이하, RTO 몇 시간.
- B2B SaaS: 고객사와 맺은 **SLA**(약속)에 맞춰야 함.

**RPO를 줄이려면 → 백업을 더 자주.**
**RTO를 줄이려면 → 복구 절차를 미리 문서화하고 연습.**

---

## 3. 3-2-1 규칙 — 백업의 기본 공식

> **3**개의 복사본 · **2**가지 다른 저장 장치 · **1**개는 다른 장소(오프사이트)

예시
1. 원본: 운영 서버의 DB
2. 복사본 1: 같은 클라우드의 자동 백업 (다른 저장 장치)
3. 복사본 2: **다른 회사/다른 지역** 클라우드 저장소, 또는 외장 하드 (다른 장소)

왜 "다른 장소"? → 같은 서버 안의 백업은 서버가 해킹(랜섬웨어)당하거나 데이터센터에 불이 나면 **같이 사라집니다.**

요즘은 여기에 하나를 더해요.
- **변경 불가(Immutable) 백업**: 정해진 기간 동안 **아무도(관리자도) 지울 수 없게** 잠근 백업. 해커가 관리자 계정을 훔쳐도 백업은 안전.

---

## 4. 얼마나 오래 보관하나 — 보관 주기 예시

| 종류 | 보관 |
|---|---|
| 매일 백업 | 최근 7~14일 |
| 매주 백업 | 최근 4~8주 |
| 매월 백업 | 최근 6~12개월 |

> 매일 백업만 7일 보관하면, **8일 전에 생긴 문제**(예: 몰래 들어온 해킹)를 발견했을 때 깨끗한 백업이 없을 수 있어요.
> 단, **개인정보는 필요 이상 오래 보관하면 안 되는** 법적 의무도 있으니 균형이 필요합니다(10장).

---

## 5. 복구 훈련 — 꼭 해야 하는데 다들 안 하는 것

**분기(3개월)마다 1번**, 아래를 실제로 해 봅니다.

1. 가장 최근 백업 파일을 꺼낸다.
2. **스테이징(연습용 사이트)** 에 복구한다. (운영에 덮어쓰지 않기!)
3. 로그인, 주문 내역, 상품 사진이 제대로 보이는지 확인한다.
4. **걸린 시간을 잰다** → 이게 실제 RTO.
5. 막혔던 부분을 "복구 매뉴얼" 문서에 고쳐 적는다.

## 6. 상황별 백업 방법

### A. 빌더(카페24·아임웹·쇼피파이 등) 사용자
- 서버·DB 백업은 업체가 해 주는 경우가 많지만, **범위와 보관 기간은 업체마다 다릅니다.** 이용 약관/고객센터에서 꼭 확인.
- 내가 할 일:
  - **디자인 바꾸기 전 스킨 복사**
  - **주 1회 상품·회원·주문 목록을 엑셀로 내보내기** → 내 클라우드 드라이브에 보관 (개인정보가 들어 있으니 **비밀번호 걸린 곳**에)
  - 상품 사진 원본은 내 컴퓨터 + 클라우드 드라이브에 따로 보관

### B. 워드프레스 등 웹호스팅 사용자
- 호스팅 업체 자동 백업 + **백업 플러그인**으로 외부 저장소(구글 드라이브 등)에 이중 저장.
- 플러그인/테마 **업데이트 전에 수동 백업** 한 번.

### C. 직접 개발 + 클라우드 사용자
- 클라우드 DB의 **자동 백업 + 시점 복구(PITR)** 켜기. → "어제 오후 3시 12분 상태로" 되돌릴 수 있음.
- 백업을 **다른 계정/다른 지역** 저장소로 복사.
- 백업이 실패하면 **알림이 오게** 설정.
- 백업 파일은 **암호화**.

## 7. 백업 폴더 이름 붙이는 법 (수동으로 할 때)

손으로 백업해야 할 때는 날짜를 **연-월-일** 순서로 붙이면 정렬이 깔끔해요.

```
backups/
├─ 2026-10-01_db.sql.gz
├─ 2026-10-01_uploads.zip
├─ 2026-10-08_db.sql.gz
└─ 2026-10-08_uploads.zip
```

❌ `백업_최종`, `10월1일`, `new_backup2` 처럼 날짜·내용이 불분명한 이름은 피하기.

---

### 이 장 요약
1. 코드(Git) · DB · 파일 · 설정 — **각각** 백업한다.
2. **3-2-1 규칙**: 3개 복사본, 2가지 장치, 1개는 다른 장소.
3. **복구 훈련**을 해 봐야 진짜 백업이다.
